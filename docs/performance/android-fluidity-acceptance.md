# Android 全应用流畅度验收记录

## 验收结论

合并 8,379 个上翻、8,346 个下翻主测应用帧，两个方向分别有 6、2 帧超过 35 ms。另 480 个延长动作中，第一组首次访问的第 31 个追加上翻产生一帧 52.40 ms，命令提交到 GPU 报告完成占 46.81 ms。合并上翻 P95 为旧包晚间 17.37 ms、v6 22.22 ms、v7 21.93 ms。v7 三组宿主忙碌率中位数分别为 47%、40.5%、14%。按两次访问和手势序号分别配对，80 个相同的上翻动作编号中有 79 个在晚间旧包上更快。模拟器宿主负载和实际媒体完成数有差异，不能将旧包早段的较高帧时当作稳定的版本收益。

六次正式访问的媒体回执在抬键后 25–42 ms 唯一匹配。每次在途峰值为 4，预热峰值为 8。共记录 603 次显示、3,182 次取消，错误、重试、超时均为 0。三组暖访自然静置 60 s，附着视图始终为 865 个。此后调用一次常规内存计数，再用系统侧读数，约 0.5 s 后相对暖访前的增量分别为 −2.59、+0.80、−4.07 MiB。保留现有媒体预算及阅读恢复策略。

收尾时独立核对主模拟器已安装普通 v7，SHA、签名、UID、首次安装时间和原输入法均与预期相符。原有三个账号仍在，首页有真实内容，四个底栏都能操作，刷新率 90 Hz。本轮按用户选择仅验收模拟器。

## 后续复现与排查

用同一 `WZ_Pixel_API_35` 主模拟器、相同内容和实际 90 Hz 节奏复现。记录普通 Release 的 APK SHA、PID、冷暖状态及每批宿主负载，采样期间避开并行构建。正式批次用轻量帧轨迹，线程栈、GPU 详细跟踪和录屏各取独立样本。按一次操作对齐输入、应用帧、系统实际呈现和画面内容。若旧包早晚结果差异很大，在相邻的安静时段用相同动作补对照。命令与采样边界见[维护手册](../operator-runbook.md#release-性能回归)。

### 重图返回

普通 v7 让首页更早可辨，但三批均未同时通过首帧和连续性门槛。两对连续超期的实际显示间隔分别为 11.81 和 11.51 ms，仍须把应用超期、屏幕停顿和可点击时刻分别记录。详细轨迹捕获了首个绘制目标延后，以及已有帧在途、新帧开工后仍需 45 至 51 ms 才呈现的情况。[分批结果](#普通-v7-重图系统返回)

从已有可读内容的首页通过主题深链打开 NodeSeek `863650`，确认重图正文。在 1080 × 2400 分辨率下，沿 `x=535` 从 `y=1890` 滑到 `670`，等 250 ms，再从 `670` 滑到 `1620`，每次滑动 170 ms。等 1.1 秒后按系统 Back，确认回到有内容的首页。每批 10 次，共三批。独立回放首页首次可辨、返回后立即点按，并覆盖顶栏、嵌套返回和关回复框后紧接 Back。[退帖测量规程](../operator-runbook.md#release-性能回归)

首页焦点隔离和分类查询移出应用根节点减少了重复渲染。保留尺寸逐项屏蔽首页文字、帖子图片、浮钮模糊，以及换静态采样源，区分出了转场中段的图形工作。整像素平移使诊断组的纹理更新面积下降约四分之三，首帧耗时落在两组默认动画的结果之间。首页临时硬件层减少了连续超期，但同步建层用时 12 至 13 ms，未纳入普通包。旧尾帧的 63.43 ms 出在 RenderThread 的 `prepareTree`，当时主线程在等待。延迟回收图片缺少现场依据。[绘制对照](#返回与回翻的渲染耗时) · [分类查询取证](#组合普通包-v3-的重图返回)

首目标迟到时，抓导航状态更新至首次 Fabric 调度的 JS 函数栈。抬键时已有帧在途，则按同一帧号追前帧占用、`postAndWait` 和 `flush commands`。等对应阶段的耗时下降，再用同一普通包复验每批首画面 P95 ≤50 ms、相邻目标周期连续超期 0 对，并另报首页可辨时间和丢弃帧。

### 搜索暖切

普通 v7 暖切前两批 P95 超过 25 ms，最慢样本是第二批最后一次从搜索回首页。该次应用帧用时 51.50 ms，实际抬手至显示为 91.46 ms。冷开已达标，继续单列。[分批结果](#普通-v7-搜索)

首页保留相同来源、筛选和列表位置。预热空搜索页，保留原有历史，收起键盘。从首页和搜索底栏来回实点，每批 10 次往返，共 60 个转向。每次等待上一转向与淡出结束后再重置 `gfxinfo`，保留至少 3 秒采样窗口，并记录真实抬手、目的页和系统呈现。同一次转向内统计相邻有效帧。[暖切测量规程](../operator-runbook.md#release-性能回归)

最近记录已改为在首次布局后显示，改词的首次 React 提交由 2 次减到 1 次。普通 v5 三批曾达标，v6 正式批次有超限与缺失数据，独立补测后来通过，v7 再次出现慢样本。各结果保留原批次；历史对照还发现重追踪会放大图形提交耗时。[普通 v5](#搜索冷开与暖切) · [普通 v6](#搜索冷切与暖切) · [追踪开销对照](android-host-chain.md#重追踪会放大图形提交耗时)

优先抓同一次搜索回首页慢样本，把抬手、导航接收、首个目标、应用完成和系统呈现对应起来，再改实际耗时的阶段。复验每批 P95 ≤25 ms、最慢 ≤35 ms、相邻有效应用帧连续超期 0 对，同时核对历史可读、来源筛选和首页位置。

### 长帖回翻

普通 v7 的 480 个主测动作没有 ≥50 ms 应用帧，额外 480 个动作中有一帧 52.40 ms，发生在第一组首次进帖的第 31 个追加上翻。命令提交至 GPU 报告完成占 46.81 ms，包含排队。晚间旧包合并上翻 P95 为 17.37 ms，v7 为 21.93 ms；宿主负载与图像完成数不同，整体收益待证。40 个独立录像动作中，24 个仍缺足够的正文纹理来判断位置停顿。[分批结果](#普通-v7-长帖与内存)

固定 NodeSeek `https://www.nodeseek.com/post-863650-1`。三组各起一个新进程，每组先在首页静置取 PID 和 PSS，再在同一进程以深链做首次和暖态两次访问。每次从匹配的起始楼层做两轮「下翻 40 次、上翻 40 次」，第一轮入主表，第二轮单列。在 1080 × 2400 分辨率下沿 `x=535` 从 `y=1890` 滑到 `670` 为下翻，反向为上翻，滑动 170 ms，命令返回后等 120 ms 再读帧。每次退帖以 `dumpsys meminfo --local -s` 采首点、30 秒、60 秒 PSS，并保留楼层和在途媒体计数。独立录屏区分手指拖动、惯性和静止，报告每百手势正文实际停住 ≥50 ms 的确认数及未决数。[滑动与内存测量规程](../operator-runbook.md#release-性能回归)

返回首帧的起点取系统向 MainActivity 投递 Back 抬起的时间，终点取此后开始生产并首次由 SurfaceFlinger 呈现的新 MainActivity 画面。它可能只画出帖子退场的开头。另行录屏确认底栏和来源栏何时能认出来，并通过实际点搜索检查输入是否已恢复。

60、90、120 Hz 的刷新周期分别为 16.67、11.11、8.33 ms。90 Hz 连续运动若错过一次刷新，相邻新位置约隔 22.22 ms。50 ms 是本项目回看手势的阈值，感觉到停顿就保留该次动作，即使整批 P95 合格。Android 将超过 700 ms 的渲染帧列为冻结帧。[Android 渲染与冻结帧](https://developer.android.com/topic/performance/issues/render#frozen-frames)

另一个常见的 AndroidX 工具 `JankStats` 使用可配置的倍数，默认值为 2。在本机所用的 Android 15 上，它把 UI 阶段耗时与「该帧系统预算 × 2」比较，同时单独记录「总耗时减去预算」。例如预算刚好为 20 ms 时，UI 阶段超过 40 ms 才会触发默认的 `isJank`，总耗时 21 ms 则已产生 1 ms 超期。两项读数都无法单独说明手指移动时正文停在原处多久。[默认倍数](https://github.com/androidx/androidx/blob/androidx-main/metrics/metrics-performance/src/main/java/androidx/metrics/performance/JankStats.kt) · [倍数计算](https://github.com/androidx/androidx/blob/androidx-main/metrics/metrics-performance/src/main/java/androidx/metrics/performance/JankStatsApi24Impl.kt) · [Android 12 及以上实现](https://github.com/androidx/androidx/blob/androidx-main/metrics/metrics-performance/src/main/java/androidx/metrics/performance/JankStatsApi31Impl.kt)

## 返回与回翻的渲染耗时

外审对三个 React 组件逐一分配的毫秒数没有函数级证据。模糊提速 64 倍、推迟图片回收就能消除长尾、普通包返回 P95 能稳定在 24–36 ms，这三项都未通过实测。首页文字会推动纹理图集更新；历史慢尾帧的主线程在等待渲染线程；长帖回翻则能单独复现原生绘制排队。三个阶段的证据与各自采用的修复见下文。

同一指定重帖的旧绘制诊断包做过 5 次返回。在每次 Back 后的 1.1 s 内，`flush commands` 下的 199 次矩形上传全部写入同一个 Skia 资源。194 次落在按键后 100–500 ms，125 个涉及上传的实际帧均画过 `AtlasTextOp`。103 帧还有 `DrawAtlasPathOp`，这个操作也能读取单独绘制的路径 RenderTarget。同资源矩形宽度均为 4 的倍数，其中多次超过 256 px；结合 Android 15 Skia 的图集尺寸，优先核查 A8 字形。另一轮旧包的 190 次重复上传均落在 `glTexSubImage2D`，属于已分配纹理的局部更新。具体来自哪个页面、哪些字形，需要绘制对照。[Skia 图集矩形对齐](https://android.googlesource.com/platform/external/skia/+/android-15.0.0_r1/src/gpu/AtlasTypes.cpp#141) · [A8 与彩色图集尺寸](https://android.googlesource.com/platform/external/skia/+/android-15.0.0_r1/src/gpu/ganesh/GrDrawOpAtlas.cpp#593) · [路径图集绘制](https://android.googlesource.com/platform/external/skia/+/android-15.0.0_r1/src/gpu/ganesh/ops/AtlasPathRenderer.cpp#321)

另在隔离设备上验证退出后续读。该组复用普通 v5 的 L 站阅读组件、楼层记录、FlashList 与原生导航，从本机读取 15 个合成重帖，每帖有 50 个回复和 256 条不同的图片描述。在同一进程依次打开各帖、滚至目标楼层、按系统返回，再打乱顺序逐一点击重开。离开与重开间隔为 24.10–158.56 s，中位 105.62 s。15 个目标楼层均在 300 s 有效缓存内，15 次均恢复原楼层、原内容行及其修订，正文与回复的读取次数均未增加。

其中 8 帖保存了 63.70–74.44 dp 的行内偏移。重开后，8 个目标行顶边的屏幕坐标均与离开时相同，63 处原生文字的坐标差为 0–1 px。另 7 帖离开时首个可读行位于屏顶下方，按现有续读规则保存行内偏移 0，重开时该行上移 58–64 px，对齐视口顶端。另选 1 帖实际退到桌面再回到应用，仍在同一楼层，6 处原生文字的屏幕坐标全部相同。

## 长文编辑器

## 组合候选 v2 的重图返回

普通包 3 批的原始结果为前两批各完成 10 次，第三批完成 4 次后，第 25 次重新进帖时应用进程崩溃。前两批输入抬起至首次实际呈现的 P95 为 66.86、75.98 ms，连续应用超期为 0、0 对。第三批的 4 次 P95 为 54.48 ms。保留原失败记录后单独冷启动同一普通包再测 10 次，P95 为 68.62 ms、连续应用超期 1 对。重测期间宿主 CPU 忙碌率中位 62%、P95 为 96%，这批无法通过 50 ms 门槛。

系统将进程退出记为前台应用异常，APK 和堆栈中的 R8 映射 ID 相符。栈指向 OkHttp 的 HTTP/2 后台读取线程，在 Okio 读取本地解码缓冲时触发数组越界。退出记录没有有效的当时 PSS/RSS。恢复同一个安装后，三个账号和四个底栏入口都仍可用。

对同一版的普通图片加载器做两个定向复现。一个线程读取图片时，另一线程取消，响应体会在读取结束前关闭。Expo 图片进度回调还可能在读取期间取消自身，使一段正常的 5 字节响应读成 0 字节。修复保留网络取消，等最后一个正在执行的读取退出才关闭缓冲。两条原失败用例和 `NetworkProxyRuntimeTest` 共 120 项通过，含 7 个本地 HTTP/2 正常读写、取消、复用或重试用例。第 25 次崩溃发生在解码响应头的局部缓冲，事发时没有足以定位到单次图片取消的记录。

三次尾样本在 Back 投递后 0.04–0.17 ms 已到达应用，系统和输入法在 0.60–0.78 ms 内确认处理完按键。可对应到首个新应用帧的目标刷新周期在 42.79–51.28 ms。此间 FrameTimeline 没有更早的该窗口帧或丢弃帧。轻量轨迹不包含应用请求 VSync 的调用点，仍无法把这段空窗分配给某个 JS 回调。另录三次 v2 返回，底栏首度可辨用了 190.70、200.51、185.74 ms，来源栏到达稳定位置用了 467.97、479.26、463.95 ms。这三次保留了绘制全程，录屏时宿主同时有构建任务。
