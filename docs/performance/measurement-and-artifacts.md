# 测量、内存与构建身份踩坑

本文保存 2026-10-18 至 2026-10-19 已核对的测量经验。数字绑定下述历史条件，不是当前版本基准。删除原件后仍能使用结论，但无法从本文还原每一帧、原始栈或完整引用链。

## 1. 测试包不匹配会让比较失去依据

**做过什么：** 对普通 Release/Hermes 包核对入口、实际 source map 模块、生成的编辑器、已安装依赖补丁、ABI、签名和覆盖安装身份。回退后重新生成 Android 工程及编辑器产物，而不是复用旧 bundle。

**已验证：** 回退基线和后续消息修复分别绑定源码。消息修复的 x86_64 与 arm64-v8a 包有相同 JS bundle，425 个实际编译模块与构建源码一致；模拟器覆盖安装前后 UID 与首次安装时间保持。四项局部优化后来也用独立匹配包验证，不能继承旧包结果。

**为什么会这样：** Git 恢复 tracked 文件不会恢复 ignored 生成物或已安装依赖。源码看起来已回退，包里仍可能带着旧编辑器或旧 patch。诊断入口与普通入口也可能挂载不同流程。

**踩坑与取舍：** 成功打包、安装成功、运行指定源码是不同判断。历史真机空白现场没有确认 APK 来源，不能证明特定候选导致空白。先重建所需生成物，再记录构建输入，避免输入快照本身过时。

**以后继续：** 使用现有[构建与覆盖安装流程](../operator-runbook.md)，先建立包身份，再比较行为。不从纯回退包通过推断后续候选通过。

## 2. 160 次滑动不等于完整流畅度通过

**做过什么：** 对历史普通包的重图主楼执行 160 次正文动作，保留间隔截图、媒体统计和重复 gfx dump，并独立去重帧记录。

**已验证：** 该轮主楼计划为 354 行、1413 个媒体；完整投影列表另计为 359 行、1414 个媒体，口径不能混用。保留的 16296 个有效去重帧得到 p95 22.428ms、worst 39.580ms、1526 个 deadline miss；7 处相邻 dump 没有重叠。间隔截图有内容，反向末尾回到标题或作者附近，没有证明精确原偏移。

**为什么会这样：** gfx 输出容量有限，采集间隔可能丢帧。动作之间的 AX 查询和截图也占时间，不能按动作数和总时长换算连续 FPS。组件 render、Native draw、实际呈现和手指到屏幕的延迟分别属于不同阶段。

**踩坑与取舍：** 截图不空白、滑动流程完成、p95 下降或 React 没重渲染，都不能单独关闭跟手问题。采集缺口不能补成没有慢帧，deadline miss 也不能由一个固定耗时阈值替代。

**以后继续：** 针对新症状取得同构建、同窗口的完整目标帧，以及 JS、主线程和 RenderThread 的对应归因。证据缺口与功能失败分开报告；不为总体通过标签反复长采。事故归属见[回归语料库](../regression-corpus.md)的 `REG-PERF-024/025/029`。

## 3. 返回后的 PSS 正增量不足以判定泄漏

**做过什么：** 对同一旧普通包、同一进程观察重图详情退出后的 meminfo 与映射，保持自然回收，不强制 GC 或清缓存。

**已验证：** Feed 基线为 363648KiB，return-330 标记样本为 405229KiB；以 Back 截图 BOOTTIME 上界另核，该次读取实际位于返回后约 340.58–340.74 秒，不能把文件名当精确采样时刻。后验自然静置约 35.07 分钟时为 369087KiB，仅比基线高 5439KiB。Dalvik Heap 与 Other mmap 已低于基线，不能继续把此前约 40.6MiB 增量称为持续未释放。35 分钟是后验观察，不是每次排查的等待要求。这些 PSS 来自后续完成的自然观察，不是下一节早期失败的 420 秒 heap 覆盖。

**为什么会这样：** PSS 包含驻留页、共享页分摊和 allocator 保留，不直接表示业务活对象。后验 Unknown 中约 65568KiB 来自 Hermes Hades 映射，只说明当时组成；基线没有逐映射数据，不能把剩余增量全归到 Hades、Worker、图片或缓存。

**踩坑与取舍：** VMA 数不等于 runtime 数，allocator 栈不等于保留根引用。异时读取的 smaps 与 meminfo 不能冒充同一时刻精确相等。HPROF 即使不要求强制 GC，也可能暂停 ART 或触发 GC，不能插入自然回收对照后声称条件不变。

**以后继续：** 若有稳定增长或 OOM，再建立匹配基线、逐映射变化和对象引用归因。没有新证据，不修改缓存容量或业务释放时机，也不重复等待固定的 35 分钟。

## 4. 目标健康门禁从失败采集到有限通过

**做过什么：** 对既有 API 35 普通 Release/Hermes 包，先做约 420 秒 heapprofd 观察；失败后离线核对目标 profile，校准流式健康检查，再完成短准入与带预算控制的业务协议。以下四轮是不同记录，不合成一次通过。

| 阶段 | 实际得到什么 | 保留的边界 |
| --- | --- | --- |
| 早期 420 秒失败 | 两个 malloc dump 相隔约 9.660 秒，末端早于首次滑动约 49.259 秒、早于返回输入约 59.339 秒；目标出现 buffer overrun、client error 和 disconnected | 183 条增减记录、110 个 callsite 不覆盖返回后 300 或 330 秒，原 partial 结论不改 |
| 流式短准入 | 首次因检查器误判首包标记而主动停；修正后 consumer 存活时读到三份完整连续的健康目标 dump，跨度约 20 秒 | 首次不能事后改成成功；最终又读到的末端包不计作新增 live 观察 |
| 带预算协议 run01 | 看图延迟耗尽 420 秒尾窗，控制器拒绝 Back | 是期限保护生效，不是 App 返回失灵；保留 partial，不放宽返回后观察时长 |
| 带预算协议 run02 | 仅把总上限调到 480 秒，完成五下五上、返回与超过 330 秒静置；最终 42 份完整目标 dump、94 次前缀核对 | 部分末端只在 stop 时读到，不能称 42 份全部 live；严格分析仍有配置警告，不宣布整体容量或无泄漏通过 |

**为什么会这样：** tracing consumer 与目标 client 是不同生命周期。目标写共享环失败后可以断连，consumer 仍记录时钟；配置期限、clock snapshot 与 consumer PID 都不证明 malloc 覆盖。健康检查必须等分片 profile 闭合，并核目标、sequence、index、时钟和错误位。协议首包的 previous_packet_dropped 也可能是带首包标记的初始化状态，不能见到该位就判丢包，更不能因此删除后续真实丢包检查。

**踩坑与已做修正：** 早期脚本最终保留 partial，但动作阶段未检查目标健康，无效采样后仍操作。后续已补齐完整目标包的阶段检查与期限拒绝，不能再把它列为尚未做过的资格探索。期限须容纳返回后 330 秒、15 秒交付与 10 秒收尾；增加总期限以保留这些阶段，与盲目增大 client buffer 或阻塞 App 不同。

**已验证的有限归因：** 后一轮 3577 条分配增减、1247 个 callsite 的抽样 alloc/free/net 为 821740456/804553032/17187424 bytes，互斥分组和端点累计核对一致。Back 后 36 个端点的 Bitmap、RN UI 与 HWUI 净余额保持，不支持把总 PSS 增量主要归因于持续增加的这些 Native 分组。Worklets callback 站点继续出现正分配，触发了第 6 节的源码调查；它仍不是对象根引用或永久泄漏证据，暖 attach 也不覆盖此前分配。

**配置警告的解释：** 当时 v58.2 processor 的 config_write_into_file_discard=1 表示配置有丢失风险，不是实测丢了一个包。连续目标 dump 与该警告可以同时成立；不能据警告否认所有目标数据，也不能删警告或把严格 NOT_VERIFIED 改成全源无丢失。此后没有为“采到警告消失”再跑长协议。

**以后继续：** 不再从同样的短准入和完整长协议原样重做。新条件确需采集时重建已确认的目标健康与预算判据，并根据新的 Java/mmap 引用或增长疑点取证；中央流式 buffer 的 RING_BUFFER 选择与目标健康仍须分别验证，不能用一种配置免除丢失检查。早期共享环写入失败的精确诱因、Java 引用与剩余 mmap 归因仍未确认。

## 5. 时间字段和文件哈希也会污染结论

**做过什么：** 复核宿主 ISO 时间、设备 uptime、Perfetto BOOTTIME 与 profile 状态时钟，并检查原件的实际落盘字节。

**已验证：** 原补充快照出现过负 8 小时的时间投影错误，修正后距可见 Feed 的保守宿主上界约 355.433 秒，仍晚于配置理论结束约 10.753 秒，不能成为有效 heap 覆盖。另有摘要对 trim 后 stdout 求 hash、文件另加 LF 的口径差异；两个 hash 不是同一字节对象。

**为什么会这样：** UTC 时间再次施加本地偏移会重复换算。MONOTONIC_COARSE、BOOTTIME 与宿主时间没有共同基点时不能直接相减。截图完成通常只是可见状态的上界，不是精确 Native 返回时刻。文本整理可能改变换行和字节身份。

**踩坑与取舍：** 修正投影或补充精确 hash 不能改写原采集结果。保留历史失败，单独解释纠正了什么，不能把后验观察补成原协议的缺失阶段。

**以后继续：** 先核时间基点和原始字节，再讨论耗时与生命周期。换单位、改标题或增加说明不能使不完整窗口变成完整协议通过。

## 6. 看到 RAF 分配，不应立刻自创 Native 释放生命周期

**做过什么：** 当轮核对 Worklets、Reanimated 与 fbjni 的 callback 创建、Java 队列和 Native peer 析构，比较默认 RAF 与提前 reset 的设想。

**已验证：** 当时 Worklets 0.10.4 的默认 UI RAF 每帧续约并创建 callback，闭包只持 weakThis，队列会清空；它能解释持续分配，但不证明 Topic 被引用。callback 的 Java 对象持有 HybridData，fbjni 通过引用队列与析构线程释放 Native peer，没有逐项 reset 本身符合机制。上游曾移除空队列就停帧的优化，因为 JSI Shared Value 后的 microtask 更新、传感器注册和 Reanimated 4.5.1 的 finalizer 仍依赖帧循环。提前 reset 仍保留 Java 与 GC 管理，还可能把析构移到 UI 线程。

**为什么会这样：** JNI 方法取得裸指针后，reset 方法的锁不会自动保护正在执行的 Native 方法。另一线程 reset、回调内自析构与重复 reset 不崩是不同安全命题，提前析构也没有消除下一帧对象创建。

**踩坑与取舍：** 当轮没有足够的真实泄漏归因与收益支持生产补丁。保留上游生命周期，不为短期 PSS 加 reset 状态机，也不把已有后台暂停行为扩成任意停帧。

**以后继续：** 只有新存活引用或持续增长指向该 peer 才重开。先以锁定依赖版本的真实 JNI 小实验验证正常、异常、后继 callback 的析构次数、线程与顺序，再评估应用收益。Mock 析构计数不代替真实 JNI 或帧时。
