# 导航与启动性能实验的经验

本文解释导航、滚动指示器和启动实验中哪些判断有证据，哪些方案没有达到采用条件，供以后选择小范围实验时复用。记录整理于 2026-10-19，不作为当前版本验收表。

当前产品契约以[产品地图](../product-map.md)为准，事故状态以[回归记录](../regression-corpus.md)中的 `REG-PERF-024`、`REG-PERF-029`、`REG-NAV-010` 为准。设备、覆盖安装、隔离构建和采样的操作规则只见[维护手册](../operator-runbook.md)，本文不另建操作协议。

10 月 13 日冷启动候选的撤回与 10 月 19 日未提交性能迭代的回退是两次不同事件。前者之后另有获准实施的机制修复，不能把某次候选未证明提速，写成所有历史工作均无效。

## 三类慢现象分别判断

| 现象 | 本来要回答的问题 | 不能混入的样本 |
| --- | --- | --- |
| 已访问 Feed 与 Search 往返 | 保留页面切换是否重复挂载、布局或绘制 | Search 首次创建、覆盖安装首开 |
| 新进程首次进入 Search | 首次 Native View 创建与冷绘制成本由谁承担 | 预热后的往返、预先挂载 Search 的候选 |
| App 冷启动 | 进程创建、本地恢复、首个 App buffer、可见页面与首批内容分别耗时多少 | 同 PID 热恢复、仅 `page-ready` 的逻辑时刻 |

首次 Search 做过独立 fresh process 采样、Native 创建归因，以及 VectorDrawable、PNG、合并图标 Path 对照。已验证首次创建和 shader 编译成本存在；未验证同一业务 View 被重复创建，也未找到稳定改善的图标替换。踩坑是把「原生节点更少」当成提速，因此这些替换没有采用，详情见 `REG-PERF-029`。

## React 渲染次数不能代表 Native 绘制

做过的归因：2026-10-18 普通真机包 d13 的六次切向有九个有效 gfx 帧，其中六个主帧错过各自 deadline。对应 Native `doFrame` 中，Search 的 main Running 约 16.9–19.6 ms，Feed 约 33.6–35.0 ms；同窗 RN JS Running 很少。已验证该样本的主体在 Native mount 和 draw，而不是同窗 JS 大段执行。

Search 三个主帧的 mount 约 9.5–11.8 ms，包含 REMOVE/INSERT。Feed 的 `Record View#draw` 约 23.8–25.3 ms，其中 `AndroidComposeView` 是包含 React 子树的父区段。它的 inclusive 时长不能全部记作 Compose 自身 CPU，也不能与子段相加。

这里有四条可复用的判读规则：

- React Profiler 的提交次数、Fabric 的 Native 指令数、View 的 invalidation 通知数和实际 draw 次数分别计量。
- 用同一 frame token 关联 `doFrame` 与 App FrameTimeline，再读同窗 Running、Runnable、Sleeping；UI 墙钟不直接叫 CPU。
- 缺少业务 View identity 时，只能定位 Native 容器或批次，不能按类名猜某个卡片、SVG 或列表是根因。
- 没有非零 error/data_loss 记录不代表全 trace 无损；info 丢弃计数、未知厂商事件和不完整时钟映射仍须保留。

本轮 gfx 只有开头 MONOTONIC 时钟快照，没有末端括定；核心线程结论使用 trace 内同 token 的 `doFrame`，gfx UI 区间仅作辅助。原采集停止后检查因空 cmdline 退出 1，随后精确清理成功，两份记录均保留，没有改写成一次全程成功。

未验证的是完整触摸到呈现延迟、JS 函数栈和长期稳定性。以后应从 [AppNavigator](../../src/app/AppNavigator.tsx) 与实际挂载 owner 继续，不因单个组件没有重渲染就排除 Native 工作。

## 导航补丁减少了什么，又没有证明什么

### 固定 zIndex 和图标宿主

做过：Android、保留页面、无切换动画的分支曾将外层 `zIndex` 固定为 0，避免焦点切换时在 0 与 −1 之间变化。已验证六个主帧的 REMOVE 与 INSERT 指令数分别从 11 降为 10，原来单条 INSERT 的长区段消失；实际编译源码对照只有 `node_modules/@react-navigation/bottom-tabs/lib/module/views/BottomTabView.js` 变化。

原因与第二次实验：两个图标 opacity wrapper 在 0/1 变化时跨越 RN 的 flatten 边界。仅在 Android 固定这两个 wrapper 的 `collapsable=false` 后，同类六个主帧的 CREATE、DELETE、REMOVE、INSERT 均变为 0；编译对照只有 `node_modules/@react-navigation/bottom-tabs/lib/module/views/TabBarIcon.js` 变化，支持该机制判断。

未验证：这两步支持「特定 Native 拆装工作被去除」，图标候选与旧包却仍各有九个有效 gfx 帧、六个 miss，Feed 实时内容也不同。踩坑是把省去的指令或 draw 绝对差值全部换算成用户收益；稳定切页改善和正式门槛均未由该单轮证明。

这两项未在 10 月 19 日回退后重新恢复。原因是重新实施范围被收窄为四项局部重复工作，不是这些 Native 指令证据失效。已有 `detachInactiveScreens=false` 属于此前提交的基线，不能误说成本次又要恢复的新增方案。

采集器另踩过一次坑：候选首轮因汇总器固定旧 PID 失败，留下的一次 Search 窗口没有混入第二轮统计。新旧包必须动态绑定各自实际进程，不能复用旧 PID 来制造完整统计。

### 可见性通知不等于尺寸变化

做过：诊断包把原有 measure、layout position、visibility 调用分别包在闭合 span 中，保持调用顺序。已验证两次转向记录 1518 个 marker、65/65 对完整前后状态，没有用时间接近代替祖先链归属。

原因与否决：Feed 隐藏/显示的 165/145 条通知，以及 Search 显示/隐藏的 44/48 条通知，全部位于 visibility 子调用，measure 和 position 各为 0。因此「只保尺寸但仍切 INVISIBLE」没有消掉这些通知的现成证据；没有实际执行该反事实，不能进一步断言它在所有环境必然无效。

踩坑与未验证：这些是有开销的诊断包记录，不是普通 APK 的性能通过。通知不是 draw，闭合 span 也不独立证明原调用成功；未验完整帧根因，不把探针并入产品或把计数下降当帧率结论。

### opacity 原型确有有限收益，也改变了契约

做过：原型在既有 Android retained、无动画分支，将 `display:none` 的 fallback 改为稳定 View 上的 opacity 0/1。React route、lazy 条件、pointerEvents 和内层无障碍隐藏保持，但 Native 宿主从 INVISIBLE、零尺寸变为 VISIBLE、非零尺寸。

已验证：真机单轮六次切向中，返回 Feed 的 draw 从约 20–21 ms 降为 1.35–1.97 ms，记录的 PageHost/列表子树不再出现在这些 draw 内。两包仍各有六个有效帧、六个 miss，且没有交错同内容对照；这是有限收益观察，不是稳定帧率、物理触感或完全等价证明。

原因与踩坑：透明度不负责暂停输入、动画和所有原生资源。隔离 GIF 对照后来确认：固定三帧 GIF 在原逻辑与候选中都能在隐藏阶段继续解码，不能再说只有 opacity 才导致它后台播放；同样不能把两边都推进当成资源已暂停。迟到加载、多消费者、CPU 和耗电没有由该 fixture 验收。

未验证：真实手机的中文 composition 对照未完成。基线软键盘覆盖全部底部 Tab，无法通过当时可见 UI 执行组合输入中切页，未通过隐藏坐标或导航后门补做。不能凭 pointerEvents 或普通输入框测试宣称 IME 等价。

原型因此未采用。以后若重开，必须先明确哪一个普通场景仍受可见性重录影响，并单独补齐输入、滚动、无障碍及实际活动资源边界；不能先添加一套全局活动状态或统一暂停所有动画。

后续入口是 [AppNavigator](../../src/app/AppNavigator.tsx)、[Avatar](../../src/ui/avatar/Avatar.tsx) 和 [SearchScreen](../../src/features/search/SearchScreen.tsx) 的真实消费者。优先确认已有焦点门禁，不新增传播到整张列表的 active props 或第二套生命周期。

## 加载动画与滚动条只解决各自的工作

做过：非当前 Feed 来源的占位显式传 `animating=false`；当前来源加载保持 true，通用 `LoadingState` 默认行为不变。该候选仅涉及 FeedScreen、共享 LoadingState 和既有 UI owner，修前两例失败、修后 owner 45 项通过。

已验证与踩坑：普通包三次返回 Feed 后原有的轻量 ProgressBar draw 消失，全部 draw 从 9 次降到 6 次。减少的是三个未 miss 的轻帧，六个主要慢帧仍 miss；不能用变高的 miss 比例否认已省工作，也不能用少三帧宣布主问题解决。

不需要为此假设整个 Feed 隐藏后仍稳定保持 busy。真实 controller 的 `feedBusy` 已受 `feedActive` 限制；把通用组件能接受的 `active=false,busy=true` 当成真实稳定路径，会引入不必要的焦点订阅。RefreshControl 的交接又是另一项，不能顺便宣布已停。

未验证：主慢帧的稳定收益、长时间动画成本和全部来源交接。该小候选可从 [FeedScreen](../../src/features/feed/FeedScreen.tsx) 与 [LoadingState](../../src/ui/controls/FeedbackStates.tsx) 独立评估，但本次四项重新实施没有包含它。

滚动条做过的实验：opacity 隐藏窗口仍有绘制，全关两轴 indicator 后，隐藏 300 ms 后的各轴绘制由 17 次降到 0。已验证这个有限对照，支持调查淡出路径，不授权永久删除当前页滚动条。

实际策略与踩坑：改为当前页开启、隐藏关闭、返回恢复后，Native fixture 的两轴标志、返回偏移、触摸目标和无障碍节点断言通过，但稳定窗口仍有纵向 2 次、横向 1 次 draw。焦点切换和淡出有过渡窗口，预设零绘制假设失败，不能换成宽松标准报绿。

未验证：该 fixture 首个隐藏样本中 fling 已结束，不证明切出边界的惯性等价。真实 TalkBack、完整生产 Feed/source pager、物理跟手及正式帧时均不由节点属性代验。Search、消息、更多的 285 项 UI 通过也只证明各自焦点接线。

这些滚动条改动未在本次回退后恢复：它们没有满足原来的零绘制预期，也不属于当前四项局部去重。后续只按产品地图中各列表的现有 owner 重建最小实验，不恢复旧试验入口。

## 冷启动实验最容易混淆的条件

同 APK 的本地启动阶段曾明显漂移；网站响应、模拟器软件渲染、shader、JIT 和主线程等待还会叠加。看到 WebView provider 或默认 UA 出现在长窗口里，不代表整段墙钟都是该函数 CPU。

| 条件或时刻 | 可回答的问题 | 不能替代的结论 |
| --- | --- | --- |
| 覆盖安装后第一次打开 | 本次安装后的启动行为 | 普通新进程启动分布 |
| 新 PID、新内核进程起点 | 进程级冷路径 | 设备冷启动、清缓存后的启动 |
| 同 PID 返回前台或再进 Search | 已访问路径恢复 | Search 首次创建 |
| `page-ready` | 当前可见 route 的布局回调到达 | 首 buffer 已呈现、可交互、帖子已加载 |
| 首个 App buffer | 对应 surface 的首帧证据 | Splash 必然已消失、首批网络内容完成 |

10 月 13 日撤回按研究前提交加当时已有 WIP 恢复，而非直接 reset HEAD；恢复了 81 个 tracked 文件并撤回 4 个本轮新增文件，保留更早改动。踩坑教训是实验边界必须能独立恢复，不能靠重放整份旧补丁继续研究。

### UA 与账号恢复：机制正确和整体提速分开

做过：调查默认 UA 常量在保存身份恢复前同步触发 WebSettings，将真实消费者迁到按需异步读取，并保留成功缓存、取消和失败语义；同时处理账号本地资料与已存 UA 并行恢复、旧身份迁移和失败重试。原因是导入期读取阻塞和恢复顺序存在真实边界，不能为了更快使用空串、伪造 UA 或失败后默认放行。

已验证：其中一些候选在 10 月 13 日撤回，10 月 14 日又按单独授权实施并取得对应行为证据。当前是否采用及具体契约由产品地图拥有；后续代码入口是 [UA 读取](../../src/platform/android/androidWebViewUserAgent.android.ts) 与 [账号恢复](../../src/features/account/useAccountRuntime.ts)，不能沿用撤回时的状态。

踩坑与未验证：UIManager 实验的提前按名读取从每次 48 次变为 0，普通启动中位数却未改善，慢样本仍保留。默认 UA 请求到主线程的排队不等于 UA CPU；行为正确和省工不能证明 `REG-NAV-010` 的间歇慢启动消失。

### 本地传输隔离需要保留业务等待形态

做过及踩坑：仅移除 INTERNET 权限触发 DNS SecurityException，是失败实验；立即返回 IOException 虽能阻断出网，却改变错误态和 WebView 回退时序。原因是「不联网」仍可能激活新的错误路径，不能直接当成原本的本地启动。

后续 v3 在真正传输前每 25 ms 等待原业务取消，上限 30 秒，两侧使用同字节拦截器，不读取地址或凭据、不调用真实传输。已验证十次样本将覆盖安装首开单列，普通顺序为 B/A/A/B/B/A，首 buffer 前传输等待尚未结算。

结果与未验证：该轮 kernel→首 App buffer 中位数约 5931→5940 ms，三个配对差有正有负，没有形成整体收益证据；Native 初始 CREATE 和 ProgressBar 数减少仍是有效机制观察。Wz 标记与内核进程起点有偏移，不能混算成一个启动指标，也未证明外站正常完成后的端到端体验。

失败版本和后续对照的历史归属见 `REG-NAV-010`。这套隔离方法服务于当次实验，不是要留在生产网络层的新功能；重开时须从当前传输边界重新证明等待、取消和零真实传输，不能要求重跑旧 harness。

### inlineRequires 没有获得采用依据

做过与已验证：编译实验只改变 `inlineRequires`，保护四个 bootstrap 的初始化顺序。同一份 5241 个 source map 输入一致，通知任务顶层依赖槽由 12→3、调用位置由 12→4；这些都不等于 App 总模块求值数。HBC 从 27,193,290 增到 27,395,426 字节，约增加 0.74%。

否决原因与未验证：实际离线 A/B 中，基线和候选普通首 buffer 都约 0.85–0.92 秒，历史数秒等待没有复现。每侧三个普通样本不足以证明尾部或稳定收益，首次非首页和真实后台任务也不能由编译测试代验，因此正常配置没有采用它。

踩坑：第一次 `export:embed --config` 没有进入实际配置加载器，两份 bundle SHA 相同，属于未生效尝试；后来才通过显式配置入口取得真正候选。只看构建命令或编译成功不够，必须核实产物确实改变且差异受控。

未采用是因为缺少当前问题上的可靠收益，不是证明该选项在所有项目都无效。未来若重开，先在当前普通包复现模块求值占用，再核对当前 Expo/Metro 的配置加载和真实 bundle；不能直接复制当时的内部配置覆盖接口。

## 再继续时先满足哪个条件

| 方向 | 重开条件与最小下一步 | 停止或否决条件 |
| --- | --- | --- |
| zIndex / 图标宿主 | 当前普通包再次观察到对应拆装；一次只恢复一个小差异，核对真实指令和四 Tab 状态 | 只有 JS 次数变化，或拆装已不存在，不叠加补丁 |
| opacity | 当前慢帧仍含可见性相关重录；先给出同内容对照和输入、资源、滚动的具体等价判据 | 隐藏资源或交互语义未闭环，不以一次 draw 更短采用 |
| 加载指示器 | 实际非当前来源仍有无用动画；复用既有两路径 owner 和普通包后续轻帧观察 | 主慢帧不受影响时只报告省工，不扩大到全局动画策略 |
| 滚动条 | 同场景能定位剩余 draw 与淡出关系；保留当前页可见与返回恢复 | 零绘制假设失败后不改阈值，也不直接永久隐藏全部滚动条 |
| 启动 / 首次 Search | 当前同一普通包复现目标慢样本；先分清新进程、安装首开和 warm，再做一次最小归因 | 症状未复现、输入身份不匹配或缺少有效窗口时停止改产品，不凭经验预挂载或加缓存 |

上述是重开研究的条件，不替代维护手册的设备操作规则，也不授权重新应用历史大补丁。

## 与当前局部改动和已提交缺陷的边界

撰写时 HEAD 为 `fa491fa1`，工作区获准重新实施的是四项：Topic 草稿更新的回复重复渲染、只枚举属性名时的重复解码、NS 同次 DOM 枚举和无表单切片、编辑器相同文档及状态的重复计算。它们没有恢复本页导航、opacity、滚动条、加载动画候选，也没有恢复 Worker 或全局缓存。

这四项有各自修前失败与修后验证，本次与手册一同纳入提交，归属见[产品地图](../product-map.md)和[回退经验记录](../../PERFORMANCE-RETROSPECTIVE-20261019.md)。本页历史 APK、Native trace 和 fixture 结果不能移作本次局部改动的验收；局部计算次数下降也不能换算为 FPS 提升。

已提交的 MVCP `stop/start` 缺陷另见[回归记录](../regression-corpus.md)中的 `REG-NAV-015`：临时停止订阅不应清掉重接后仍需要的补位配置，显式禁用才清理。真实 helper 的失败断言支持该缺陷，但尚不足以完整归因具体手机的大面积空白现场，不能把它反推成上述每个导航实验造成的结果。

历史临时附件不作为本文的使用前提。正文保留做过的实验、已验证结果、机制解释、踩坑和未验证范围；后续从当前源码和权威文档重建必要的最小实验，不默认恢复任何旧候选。
