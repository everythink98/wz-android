# 消息协议与保留列表回归踩坑

这些问题在性能探索期间暴露，需要用协议与生命周期证据分别判断。2026-10-19 先回退全部未提交探索，再用匹配基线包复查；不能按发现顺序认定由最新性能候选引入。

## 1. 同一批消息被误当成无限分页

**做过什么：** 在回退基线打开 NS 消息分类并滚到底，核对真实请求次数、去重结果及原站前端调用；只读比较两个页号的实体序列。

**已验证：** 旧包回复停在 40 条、全部停在 60 条却持续加载，一分钟分别有 168 次和 59 次成功列表读取。两个回复页号返回相同 40 个原始 ID，没有分页字段。原站三组列表读取无 query 的完整数组，不翻页。后来修复包数据变为全部 62、回复 42、@我 15、私信 5 条，四类均正常结束，未读有数据和为空也结束。

**为什么会这样：** App 用原始行数至少 30 猜测下一页，服务器忽略页号；UI 去重后条目数不变，却仍收到可续读标记，触底继续请求。请求每次成功，因此 spinner 不代表某个 HTTP 一直挂着。

**踩坑与已做修复：** 不增加重试、不只停 spinner。请求与原站一致，保全当前有效行，正常列表明确无下一 cursor；不截断，也不把失败当成空列表。“完整”指原站当前提供的快照，不承诺可翻到全部历史。

**以后继续：** 原站协议若改变，先证明新分页字段与相邻页实体关系，再改 adapter，不能恢复条数猜页。入口为 [NS 消息 adapter](../../src/sources/nodeseek/notifications.ts)及其[测试](../../src/sources/nodeseek/notifications.test.ts)。

## 2. 服务端错误被叫作返回格式不正确

**做过什么：** 将旧包两次格式错误与同一请求的状态、Content-Type 关联，再用真实 adapter 的受控响应建立修前失败断言。

**已验证：** 两次现场为 HTTP 503、text/html；旧代码先 JSON.parse 再判断 HTTP 状态，因此进入 invalid_response。修前六项分类断言失败，修复后保留 HTTP 状态，相关错误与消息解析 owner 通过。

**为什么会这样：** HTML 错误页不是 JSON，但服务不可用与成功返回坏数据是不同问题。先解码抹掉传输证据，也使恢复动作难以区分。

**踩坑与已做修复：** 保留 CF 与鉴权分层；HTTP 成功却 JSON 或 schema 错误时仍报错。不统一吞成空数组，不统一要求登录，不放宽校验掩盖原站异常。

**以后继续：** 新现场分别记录 HTTP、解码、schema 与业务确认，按现有 owner 补最小反例，不重建错误状态机。

## 3. HTTP 成功不等于全部已读业务成功

**做过什么：** 沿三组 POST、写后新 GET、runtime 持久化计数和导航徽标追踪确认链，用真实 Route、gateway 与 adapter 的受控 transport 验证。

**已验证：** 旧 adapter 丢弃业务回包，某组 2xx 返回空对象仍可能宣称成功。三组各自缺少确认的断言修前失败；修复后必须逐组收到 success 为 true，未确认就停止后续组。受控正常链要求新的 GET 为零、runtime 与持久化计数归零，导航另验证徽标增删。Live 时 NS 有两条新未读、另两站为零，Native 红点正确保留。

**为什么会这样：** transport 接受请求与服务器完成业务不是同一确认。红点汇总所有启用来源，NS 读完不能推出其他站没有未读。失败时保留可信旧数，也不是计数残留的充分证据。

**踩坑与已做修复：** 不强制本地清零、不隐藏徽标伪装成功、不复用写前 GET 对账。发送失败、业务未确认和原站仍有未读保持可区分。

**未验证：** 没有代操作真实账号批量已读。受控链与 Native 徽标分层测试不等于真实三组写入到徽标消失的完整端到端通过。

**以后继续：** 若仍复现，保留同一身份的三组业务回包和写后计数，核对各来源贡献，不能随意清登录态或替用户修改消息。

## 4. 临时 detach 被当作永久关闭

**做过什么：** 用户报告“消息→首页→消息”空白后，核对 RN 滚动补位 helper 的 stop/start、两轴 View 的 detach/attach 与显式关闭；用真实 Native helper 建立失败断言。

**已验证：** 已提交补丁在 stop 内清配置及累计补位，临时重接只执行 start，不会重发未变化的 prop。修前 stop/start 用例期望 scrollY 680、实际 600；修后七项 Native owner 通过，显式禁用仍清旧周期。匹配修复包滚动后切首页返回三次，均保留六条可见消息及结束提示。

**为什么会这样：** 退订更新事件与放弃业务配置是两件事。保留页面暂时离开 Native window，返回后仍属于同一滚动周期。把清配置藏进通用 stop，重接后没有新 prop 恢复状态。

**踩坑与已做修复：** 临时 stop 只退订，保留当前配置与锚点校正；两轴显式关闭先清配置再释放 helper，没有另造页面生命周期或返回栈。

**未验证：** 特定手机大片空白与该缺陷的完整因果未闭环，历史现场 APK 来源也未确认。修前普通基线三次切页未复现，修后有限切页通过，都不能证明所有偶发空白消失。

**以后继续：** 再出现时先保存包身份、滚动位置、Native 节点与回切动作，区分没有数据、内容布局偏移和未绘制，不能默认再改导航保活、透明度或列表高度。入口为[现有 RN 补丁](../../patches/react-native+0.86.3.patch)，当前事故查[回归语料库](../regression-corpus.md)的 `REG-NAV-015`。

统一回退的对象是当时未提交代码。`a460a914` 中已有错误分页和滚动补位清理缺陷，所以回退后仍需单独修复。消息修复后来提交为 `fa491fa1`；这不证明更早性能改动全部无关，也不证明四个用户现场有同一根因。
