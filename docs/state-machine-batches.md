## 批内实施与批末验收

1. 从上一批已验收提交开始，记录本批实际改动范围和原有未提交改动。先追踪调用方、消费者及共享状态，再按完整 owner 实施；同一文件由一个执行者负责。
2. 批内按行为运行定向测试和必要的局部静态检查。同一行为或共享测试集中运行，不为每个 ID 重复整套测试、构建和设备验证。
3. 本批稳定后，集中运行一次 `npm run typecheck`、一次 `npm run verify` 和一次普通 Android 开发构建。具体构建、Native 和设备命令遵循[维护手册](operator-runbook.md)，不用正式发布流程代替开发构建。Native 和设备检查按实际影响范围合并安排；未变的无关 Native 用例不重复运行。
4. 用户流程、登录、存储、布局、WebView 或原生生命周期发生变化时，对受影响入口集中做一轮匹配 APK 的模拟器验证。首页手势、Topic 定位续读等专项要求遵循[测试标准](testing-standard.md)，不能用 App 启动代替完整流程。
5. 对本批每项记录实际结论：完成转换或删除、保留及理由、尚未解决及证据缺口。只有完整范围已处理且相应证据成立的项才能计为完成；保留或不确定项不能算作已消除。
6. 验收通过后做一个本地批提交，再进入下一批。正常路径共 10 次批末全量验收、10 个批提交，当前回退点另计；必要的失败修复和重跑不受次数限制。

遇到失败先保留输出和随机 seed，最小重现并修复根因，再补跑失效的检查。只有无法安全完成时才精确撤回本批自有差异，保留此前已验收提交与用户改动。回退不使用 `reset --hard`、`clean`、卸载 App、清数据或模拟器快照恢复。本任务不 push、不合并、不发布。

## 共享实现与跨批契约

171 个源码 owner 文件组和 11 个 SDK 包均完整归属同一批；编辑器文档的 13 项和 WebView host 的 6 项没有拆分。数量在 22～36 项之间，因为 Native 与 SDK 工作不能仅按条数衡量。P09 包含通知消息、系统文档选择两个独立子组，分别做定向验证，共用一次批末验收，不合并业务状态。

按 P01～P10 顺序推进，但每批必须复核相邻契约：P01 的草稿与提交持久层连接 P06 编辑器；P02 网络与 Cookie 事务连接 P03 账号恢复；P04 共享键盘与页面面板连接 P06 原生编辑器；P05 Topic 动作连接 P06 提交与返回定位；P07 媒体资源连接 P08 图像预览与渲染。先处理的一侧保留现有协议并验证消费者，后处理的一侧重新验证同一契约。如果具体方案必须改变协议，则在同一次实际改动中迁移实现和调用方，不能提交不兼容的中间状态。

独立时钟、数值几何、资源句柄、公开 API、动态字符串调用和 SDK 生命周期不能为了减少计数机械合并。删除前需要证明没有调用方、入口可达路径和测试依赖；不能证明的保留并说明理由。产品能力与现有行为以[产品地图](product-map.md)和实际代码为准。
