# 架构说明

## 文档职责

- `docs/product-charter.md` 定义产品目标、核心旅程和取舍标准。
- `docs/product-map.md` 定义现有能力、用户入口、能力 ID 和共享回归范围。
- `docs/regression-corpus.md` 记录历史逃逸问题的状态、关联能力、症状与根因，以及当前 owner 或取代关系。
- `docs/code-standards.md` 是代码 ownership、import、测试归属和质量门禁的唯一规范。
- `PRODUCT.md` 只维护品牌、视觉和 accessibility 约束，不作为产品范围或实现事实源。
- 本文只回答这些能力“怎么实现”：记录当前 module、interface、数据和原生配置边界，不重复完整功能清单，也不维护版本号或登录状态。
- `docs/testing-standard.md` 定义测试 owner、证据层和验收强度，`docs/operator-runbook.md` 定义开发、设备与发布操作。
- `memory/` 与 `docs/emulator-baseline.md` 保存本机事实，不进入 Git，也不作为共享架构规范。

## 当前范围

本仓库是阅坛 Android App。App 面向 NodeSeek、linux.do、V2EX 和妖火，提供本地优先的多网站发现、搜索、续读和必要互动能力。四站共享阅读主干，互动能力按原站真实支持范围提供，不要求对齐。

## 主要结构

| 路径 | 作用 |
| --- | --- |
| `App.tsx` | 应用入口，提供唯一 `QueryClientProvider` 并加载 `AppRoot` |
| `src/app/` | `AppRoot → AppComposition → AppRoutes → AppNavigator` 组合链、导航命令与 App 级 runtime 投影；不拥有 Screen、细粒度 controller 或具体来源协议 |
| `src/domain/` | 无 React、无 I/O 的 Forum、ReaderData、Session canonical model 和确定性规则 |
| `src/features/` | Feed、Search、Topic、User、Library、Account、More、Notifications 用户旅程的 controller、screen、局部组件与样式 |
| `src/sources/` | `readGateway`、notification gateway、聚合读取、Discourse 协议与四站独立 parser/reader/account/action adapter |
| `src/platform/` | Query、网络、存储、诊断、媒体、更新、通知调度和 Android bridge |
| `src/ui/` | 跨旅程复用的 primitive、TopicCard、Avatar、导航控件和主题 token/context |
| `src/platform/query/serverState.ts` | TanStack Query 的唯一 client，以及四站类型化 query/mutation key |
| `src/sources/readGateway.ts` | App 统一来源读取入口，隐藏四站读取 adapter 差异 |
| `src/sources/discourseRead.ts`、`src/sources/discourse/actionRequest.ts` | 当前 linux.do 读取鉴权组合与标准 Discourse 写请求建模；站点 transport 仍独立 |
| `scripts/check-architecture.mjs` | 六类根目录、import 方式、依赖矩阵、组合链 allowlist、旧路径、barrel 和循环依赖门禁 |
| `plugins/` | Expo config plugin，持久化 Android 原生配置；服务器代理、通用 SecureRandom 与预览区域解码原生源码分别由对应 owner 生成 |
| `scripts/` | 文档检查、Android smoke、release 打包与版本检查脚本 |

`AppRoot` 只渲染 `AppComposition`；`useAppRuntime` 只组合深 runtime 并投影七个 route capability；Account runtime 自己创建全局 host 节点，`AppComposition` 只把该节点与全局 provider、routes 声明式挂载。routes 等待统一 ReaderData 与本机账号终态恢复共同结算，不等待代理 SecureStore 或原生 apply；`reader-settings` sidecar 在 ReaderData 有界加载内合入，不形成第二个 route gate。两类本机状态尚未结算时，`AppComposition` 显示静态、可访问且无动画的启动状态，不能返回空节点或启动 Feed/Categories transport。`AppRoutes` 是七个 feature route entry 的唯一映射；`AppNavigator` 只接收 route component，不 import feature。四个 tab 使用 React Navigation 默认 lazy，只在首次访问时挂载；访问后保留输入、筛选和滚动状态，并以 `freezeOnBlur` 暂停失焦树的重渲染。Feed/Search/Library/User 共用 `useAppRuntime` 按 `favorites + history + listDensity` 建立的唯一 `TopicListItemStateIndex`，无关 ReaderData 变化不得重建。

## 来源边界

- Feature controller 通过 `src/sources/readGateway.ts` 的 `getFeed`、`searchTopics`、`getTopic`、`getReplies` 和用户资料 interface 读取四站数据；NodeSeek username 定位只通过 managed `resolveNodeSeekUser` 进入 `src/sources/nodeseek/reader.ts`，Controller 不直接调用具体 provider。
- `src/domain/forum/sourceCatalog.ts` 是来源集合的唯一静态事实源；来源类型、四站主 `baseUrl`、规范来源顺序与 Search 聚合顺序、筛选状态、managed session、credential/诊断枚举、页面 action capability 和 NodeSeek canonical host 判定都从这里派生。当前所有来源都进入 Feed/Search，不维护恒真的逐站聚合开关；既有 provider protocol 常量只 alias catalog 值，登录、迁移、链接、读取与 action endpoint 从对应 `baseUrl` 组合。SoV2EX、NodeImage、`connect.linux.do` 等独立服务仍保留各自协议边界。
- `sourceCatalog` 只描述 App 支持什么；`ReaderSettings.contentSources` 描述用户启用什么以及展示顺序；Account canonical identity 描述当前账号事实。`src/domain/reader/contentSourcePreferences.ts` 负责清洗旧设置、补齐新来源并投影唯一 enabled set 及 Session/Notification 子集，Feed/Search 直接消费同一 enabled set。页面按用户顺序展示，“全部”固定第一；Query 和 cursor 使用按 Catalog 规范化的 enabled-set key，因此重排不触发网络，启停才切换请求快照。
- 四站的首页、搜索、主题、回复和用户资料读取均已进入 managed gateway：`createReadGateway` 组装 WebView fallback fetcher、Cookie、User-Agent、凭据 generation、妖火失效清理和直接的 linux.do read auth 投影；Query function 只传业务参数、TanStack `AbortSignal` 和诊断 trace。
- `src/domain/forum/readPlan.ts` 按 `source + operation` 把一次读取纯派生为 `local`、`public`、`authenticated` 或 typed `blocked`；ReadPlan 不持久化，也不是新的流程状态机。公开 lane 只使用 `native-no-cookie` transport，并在 Gateway 强制 `credentials: 'omit'`，不读取 Cookie、SecureStore 或启用 managed WebView fallback；authenticated lane 才使用受管会话。V2EX 公开读取，NodeSeek/linux.do 的 Feed/Search/Topic/Replies/Reply/User Profile 允许公开读取；用户名解析、筛选候选、AI、等级及其他私有能力保持严格。妖火只有 Categories 为本地能力，所有远程读取都要求已确认会话。每个 Query key 和聚合 child 都绑定 ReadPlan `cacheScope`，计划改变会使迟到结果 stale。
- App 冷启动并行读取 ReaderData 与每来源持久化账号终态；两者结算前只显示启动骨架。正常启动不做 Account probe，恢复完成后从唯一账号快照派生一次 ReadPlan，再分别启动一次 Feed 与 Categories transport，不等待 `Linking.getInitialURL()`。首次升级没有账号快照时，只对当前已启用且确有 Cookie/SecureStore 候选的来源做一次有界精确核对，完成或失败后写一个全局迁移 marker；以后不自动补核。Feed 首次 `FlashList.onLoad` 与 Categories 终态共同标记首屏完成，之后才启动自动更新和远端通知。外部 Topic link 只保留 navigation-ready 前排队与之后直达的正确性，不参与普通启动门禁，也不作为冷启动性能目标。站内从 Feed/Search/Library/Notifications 进入 Topic 后，同一 query key 的返回再进入直接复用唯一 `QueryClient` 的进程内 RAM 数据；默认不因 mount/focus/reconnect 重取，UI 不重编译正文，不建立第二套缓存。真实身份、ReadPlan、来源设置变化和用户显式刷新仍通过新 key 或明确命令合法读取。`reader-settings` 缺失、损坏、非对象、读取拒绝或超过 3 秒时，内容源回退为四站全启用并保留已成功读取的 ReaderData；迟到设置不得二次发布。headless 通过同一 `loadReaderSettings()` 取得相同默认值。`ReadGateway` 和 `NotificationGateway` 在读取 Cookie、SecureStore 或 adapter 前检查当前 enabled set，并在异步返回后复核；聚合读取只遍历 Query key 捕获的 `includedSources`。停用会精确取消该站和旧 enabled-set 的聚合 Query，迟到结果不得提交；Topic、User 与 NotificationDetail 在 route 外层显示停用态，不挂载远端 controller。ReaderData 自身损坏或读取失败继续进入既有只读恢复模式，不用设置默认值覆盖用户资料。
- 用户链接先归一为轻量 `UserReference`，只承载 source、可选 id/username、原站 URL 和展示 hint；它不是完整远端资料，不能进入 ReaderData 或关注。NodeSeek `/space/{uid}` 直接形成 canonical reference；`/member?t=username` 始终形成内部 reference，当前 Topic/detail candidates 只提供有界数字 UID hint，miss 不改变内部导航判定。username-only resolution 按严格 ReadPlan 解析 canonical 数字 UID；已有 canonical UID 的 Profile 可按公开 ReadPlan 读取。Profile、主题、回复、分页与关注随后只消费完整 `UserProfile`。Discourse 只有明确 username 才形成 reference，display label 不参与身份推断。
- linux.do 是当前唯一 Discourse adapter；`src/sources/discourseRead.ts` 直接组合其 reader、鉴权投影与 `discourseModel` 等无站点偏向模块，不维护单实现 registry。无站点偏向且语义相同的 cooked HTML 归一化（安全头像、引用 label/username 分离、reply quote 的完整 `source + topicId + postNumber` 身份，以及 Callout 协议）放在 `src/sources/discourse/content.ts`，站点 transport 与鉴权仍归 adapter。
- Discourse Callout 的 canonical 类型与固定 registry 位于 `src/domain/forum/callouts.ts`；linux.do adapter 在 `sanitizeContentHtml` 的同一次 DOM parse 中归一化为仍以 `blockquote` 为根的 App canonical 结构。normalizer 只识别首段开头的 `[!type][+/-]`，清除来源伪造的 `data-forum-callout-*` 与 `forum-callout-*` class，再写入固定 type/fold/title/content/tone 标记。compiler 只把 source `fold` 解释一次并产出 typed header 的 `defaultExpanded`；`TopicSplitDisclosureStore` 是展开状态与 body-row 过滤的唯一 owner，`src/ui/content/ForumCallout.tsx` 只渲染受控 header、配色与无障碍语义，不拥有正文或 fallback state。普通引用和非 Discourse 来源继续走默认 renderer。来源 `style`、动态 CSS/JS 和自定义颜色不进入该信任边界；标题链接仍走统一内部导航并阻止折叠冒泡。主题正文、回复、同/跨主题引用、采纳答案和超长分块共享这一 renderer，入口组件不得再各自解释 Callout marker。
- 标准 Discourse 回复、点赞、书签、编辑、删除、投票和上传先表达为 `DiscourseAction`，再由 `src/sources/discourse/actionRequest.ts` 构造请求；Topic controller 通过 linux.do action client 执行统一 action 生命周期。
- Feed、Search、Topic UI 只消费语义筛选、权限和 action capability；标准 Discourse emoji 目录由 source-scoped `forumQueryKeys.emojiUrls(source)` Query 作为前台权威状态，Topic 与 NotificationDetail 复用同一结果，并通过 managed `readGateway.getEmojiUrls` 复用代理 fetcher、站点凭据、诊断和 `AbortSignal`。adapter 的站点级目录缓存只负责 transport memoization，不拥有页面生命周期或 UI 状态。linux.do boost 与 Cloudflare 验证留在站点 presenter、鉴权或 transport 边界。
- App controller 使用不带 `Direct` 和站点前缀的通用读取入口；妖火的 `Direct` 命名只保留在 gateway 后的来源实现。
- `readGateway` 分别转发到 `feedRead`（Feed/Categories 聚合）、`searchRead`（Search 聚合）和 `sourceRead`（Topic/Reply/User 单来源分发）；来源实现集中在各 provider reader，当前唯一 Discourse 来源由 `discourseRead` 直接组合。
- 聚合读取只组合结果、错误与诊断，不拥有 Cookie、凭据、Query 或页面状态；这些边界仍由 `readGateway` 和调用它的 Query owner 持有。
- NodeSeek 以 `protocol`、`feedParser`、`topicParser`、`userParser` 和薄 `reader` 分离协议、列表、主题/回复/投票、用户/账号与 I/O；linux.do 复用无站点偏向的 Discourse normalizer，并保留 `search`、`account/level`、鉴权和 reader；V2EX 分离 `reader`、`search`、`account`，妖火分离 `sessionParser`、`feedParser`、`topicParser`、`userParser` 与 reader。NodeImage 已有独立授权边界，不为目录对称继续拆分。
- NodeSeek 私有正文只有三个 owner：`prepareNodeSeekForumContent` 在一次 DOM 遍历中识别并净化 poll/Stardust marker；薄 `reader` 在当前读取窗口内去重远端 poll，并按每段正文自己的 ID 集合绑定 `Topic.polls` 或 `Reply.polls`；`compileForumContent` 在 marker 原位置产出既有 poll row 或 Stardust typed element。opening、首屏评论、分页评论与定位评论不得另建解析器、renderer 状态或页面级投票归属；投票选择/提交和 Stardust 付款仍由既有 action controller 独占。
- Forum HTML 的通用解析与 `text/attribute/full` 三种固定转义分别归 `src/domain/forum/html.ts`，内容净化/终端转换和访问限制分别归 `src/domain/forum/contentSanitizer.ts` 与 `src/domain/forum/accessRequirements.ts`；来源 adapter 只能在这些确定性边界前后处理自己的协议差异，不另建可配置 escape 规则。
- NodeSeek 的 `topicParser` 在共享内容入口恢复同条评论完整 ANSI 源码；rendered 路径按源/目标两侧唯一的评论 ID 或楼层取源码，块数量一致才按原顺序配对。只替换终端显示子树并保留周边 DOM，父节点批量提交，避免逐兄弟替换复制数组；不以整个 Markdown 替换已渲染正文，不引入第二个 Tab 解析器、就绪轮询或图片等待。通用 sanitizer 同时接受有/无 `xterm-row` class 的有序行。
- linux.do 回复窗口先保留没有 `deleted_at` 的 `user_deleted` 候选，再由同一个回复归一化入口只接受含可渲染作者删除占位的正文；初始、正向、反向、目标窗口与单条回复读取不各自过滤，也不改 `post_stream` 游标和偏移算法。原始窗口 helper 只验证 fetched window 的身份、重复项与完整性；展示排序 helper 处理归一化后的任意子集，空集返回 empty partial，混合子集仍按 `post_stream` 顺序及 newest 反转排列。真实 `deleted_at` 与空占位继续缺失。
- linux.do 只把来源明确的 `div.math`、`span.math` 归一为 block/inline canonical 公式标签；普通 `$...$` 不推断。Topic 现有 compiler 与 HTML renderer 是主楼、回复、展开引用和采纳答案的共享 seam；一个模块级 Promise 初始化唯一的 MathJax TeX/SVG/MathDocument，固定使用 `@mathjax/src@4.1.3`、NewCM 4.1.3、静态注册的全部 40 个 NewCM SVG dynamic ranges 和 `fontCache: none` 生成独立 SVG，再交给现有 `react-native-svg`。SVG 几何接受 `viewBox` 或 `data-mjx-viewBox`，百分比宽度按正文容器换算且保留 MathJax 原始变换。块公式成功与 TeX fallback 共用 content-boundary spacing，正常上下文保留 `8dp`，物理 continuation 只裁对应人工边界。等待或失败保留原始 TeX；不使用 WebView、远程字体、自动重试、公式缓存或页面级状态机。
- Topic 共享内容 compiler 是安全正文的无损展示变换：主楼、回复、展开引用与采纳答案必须保留净化后节点的内容集合、DOM 顺序和选择 tape。`compileForumContent()` 一次产出不可变的 `row.html`、`selectionToken` 和有序 `previewImages`，运行期不再 materialize 或解析 HTML。Topic Presentation Contract 把作者位置、媒体能力和文档生命周期分为正交轴：sanitizer 清除来源伪造的旧/内部 marker，compiler 只从块边界和 `br` 作者行重算可信 standalone context；mixed 图片在原 DOM 锚点走 textual projection，standalone 图片仍在同一锚点但直接复用既有 block image owner，明确的 figure/lightbox 保持显式 block。block/textual projection 共用 compatible SVG artifact、原图请求 layer、媒体 coordinator、请求 identity、尺寸缓存、预览目录和 generation 结算；局部内容宽度只影响 frame，不反向分类位置。来源 adapter 只能在 sanitizer 之后写入可信 marker，renderer 不按来源、URL、class 或加载后尺寸猜测语义或改写位置。未识别、未准入或失败的安全图片必须保留完全转义的非空降级内容，危险 URL 仍由 sanitizer 拒绝。
- 来源静态 capability 只说明该站可能支持某项能力；当前主题或回复的 `canEdit`、`canDelete` 等权限仍以原站解析结果为准。

## 服务器状态与请求生命周期

- Feed、Search、Topic/回复/引用、User、Account 和等级读取由 `src/platform/query/serverState.ts` 的唯一 TanStack Query client 统一拥有。内容 key 固定以 `forum -> source -> resource` 开头，只包含会改变响应身份的结构化业务参数、ReadPlan `cacheScope` 和非敏感 `ForumSessionEpochs`；Account snapshot 使用稳定的 `account -> source -> snapshot`，不含内容 epoch。账号精确核对只使用 controller 内按来源 single-flight 与 generation/Abort 所有权，不建立第二类 Query key。NodeSeek username resolution key 只含精确 username、严格 ReadPlan scope 与 session epoch；canonical Profile key 只含 source、数字 userId、ReadPlan scope 与 session epoch，不含 username 分叉。Infinite Query 的页码与 cursor 只放在 `pageParam`，Cookie、token 和序列化 request key 不进入 key。内容 `use*Controller` 只组合 Query result 与页面本地状态，不复制远端 data/loading/error，也不再拥有 transport request id、owner map、generation 或 Abort ref。
- Search 聚合预览与单站分页保留 `preview/pages` 两条 typed lane；聚合 key 使用逐站实际生效的排序。Controller 仅在除 lane 外的来源、关键词、筛选、排序、ReadPlan scope 与 session epoch 完全相同且目标分页缓存为空时，把成功预览的完整第一页包装成 `{ pages: [result], pageParams: [1] }` 提升到分页 lane，并保留预览的 `dataUpdatedAt`；目标已有数据时，无论预览新旧都保留全部分页。两种数据形状不得直接共用 Query key，身份不匹配、显式重搜/重试和下一页继续走 Gateway。
- 状态按事实与生命周期划分，不按变量形状合并：Query 拥有当前远端事实；Search draft/submitted、Feed 单一 `feedSource` 和妖火 Topic 稳定布局分别是搜索输入、来源选择与渲染连续性的 route 投影；ReaderData state/ref/persistence、App screen/ref、通知 headless baseline、Native runtime 投影与媒体 transport cache 服务不同生命周期。commit-safe ref 只桥接命令式回调，不是第二个 writer；只有同一事实、同一生命周期且可互相写回的副本才应删除。
- `src/platform/concurrency/keyedSerialRunner.ts` 是进程内按 key 串行提交的唯一 primitive；账号 session、credential vault 和 notification worker 分别创建独立 runner，同 key 串行、不同 key 并行，失败不得阻断后续任务，settled tail 必须释放。无 key 的全局队列不进入该抽象。
- Feed/Search/Topic/User/等级的 Query `queryFn` 只使用 TanStack 提供的 `AbortSignal`，并直接传给 managed `readGateway`。`useAccountStatusController` 是稳定 snapshot 的唯一提交 seam；同来源并发核对复用一个 Promise，核对 activity 只写 `isVerifying`，不改身份事实或 ReadPlan。`readGateway` 负责 enabled set、ReadPlan/current scope、epoch、adapter、transport 和标准化错误，不承担 UI 请求归属。已确认身份在核对、网络、解析、403、429 或验证失败时继续有效；真正 unknown 的来源不阻断公开计划，严格计划在 transport 前返回 `identity-pending`、`identity-unavailable` 或 `login-required`，供页面结算并提供对应恢复动作。来源返回失败、需要验证或 `parse_empty` 时不保存为可信数据；刷新或分页失败由 Query 保留此前可信 data/pages 和 cursor。

- `src/sources/forumSourceReadAttempt.ts` 是读取 runtime 轮换的 source-proof 与最终请求所有权边界。NodeSeek/linux.do 的 transport fallback 只能把同一 `Response` 登记为候选，不能因 HTTP 200 直接轮换；具体 source parser 以 Response proof 接受或拒绝证据。单站 `ReadGateway` 与 `accountRead` 只在 typed operation 成功后提交；Feed/Categories/Search 聚合 child 即使先解析完成也只把自身 proven evidence 暂存到 aggregate attempt，全部 sibling 结算并形成最外层 typed result 后才统一提交，另一站成功不能替失败站证明。Gateway eligibility 随 fetcher 传入聚合 child；最终 Gateway session generation 必须仍 current、所属 signal 必须未 abort，且多个 evidence 在每次 commit 前重验，失效后不再提交后续证据。一个 operation 内主请求与可降级辅助请求各自结算：辅助 poll/分类 hydration 的解析失败被吞为 partial 时不得确认自己的候选，主 fallback 已被证明时其后的辅助 direct 成功也不得抹掉主证据；另一条更新且已解析成功的 direct operation 则使旧迟到候选失效。无 attempt scope、aggregate 失败或最终 owner 失效时 fail-closed，合法空 JSON/明确匿名仍按 adapter 成功契约提交，rotation 失败和 attempt 门禁都不改变已解析结果及 Gateway 原有取消语义。
- linux.do LV2+ 等级读取先直连 Connect；只有响应未形成可解析官方卡片时，`level` adapter 才用内部 Account intent 把精确的 `GET https://connect.linux.do/` 交给既有隐藏 WebView 一次，以完成站内 SSO 并读取最终页。该恢复不是通用 retry，不覆盖其他 URL、方法、等级或取消状态，失败后仍保留本机估算。
- 正常启动只恢复本机终态，不遍历来源核对。更多页公共刷新并行核对当前已启用 managed 来源，每来源沿用既有 5 秒预算且同来源 single-flight；开始、超时、断网、403、429、Cloudflare 或解析失败均保留原 snapshot 和 ReadPlan。逐站账号状态只影响对应 operation 的 ReadPlan scope，不能形成全局 barrier。
- 聚合 Feed/Categories/Search 为每个 included source 捕获显式 child ReadPlan 与 fetcher；每个 child 复用 `withAbortableTimeout` 的连续墙钟 5 秒预算，保留 typed `aggregate_timeout`、统一取消文案和父 signal 预先取消时零 child 调用。公开 child 可在其他来源 unknown 时独立结算，严格 child 以 typed blocked 终态退出而不发 transport，另一站成功也不能证明它。Controller 只保留当前 enabled set、ReadPlan scope 与 epoch 仍匹配的可信页；计划或身份切换取消旧请求、关闭旧 cursor，并拒绝迟到结果。NodeSeek 与 linux.do 的受管 WebView 队列仍按获授权写操作、前台可见读取、后台账号健康检查排序，同级 FIFO；公开 lane 不进入该队列。
- 稳定 Account Query 中的 `AccountSessionSnapshot` 是前台 JS 生命周期内每来源唯一账号事实，包含 status、currentUser、cookieSummary、lastVerifiedAt、lastError、`isVerifying` 和 `identityTrust`。`identityTrust` 只有 `confirmed | unknown | none`；`isVerifying` 只表示核对 activity，不改变原身份事实。每来源的 `account-session.v1.*` AsyncStorage 记录只持久化 authenticated 的最小非敏感 identity 或 anonymous 终态；允许字段为 source/id/username/displayName/avatar/url，不含 Cookie、token、密码、Cookie 摘要、topics 或活动。单来源损坏独立降为无记录；全局 migration marker 只记录旧安装迁移已尝试。WebView/授权 workflow 只表达弹层、检测、授权与对账生命周期，不复制 session、identity 或 error；`identityKey`、authenticated、isLoggedIn 与 canWrite 都从同一 snapshot 纯派生。UI 通过 `useQuery` 观察，ReadPlan、写门禁、NodeImage、前台通知和媒体通过 `queryClient.getQueryData` 同步读取；Headless notification 仍在自己的 JS 生命周期现场复核。
- 身份 A→B、A→anonymous 或已知 anonymous→B 时立即提交内存 snapshot，再递增目标站内容 epoch 并移除该站旧 authenticated Query、等级/AI、Topic 服务端数据及媒体身份缓存，随后按来源串行落盘；A→A 只更新资料并落盘，不推进 epoch，首次 unknown→可信身份也不伪造换号。原始 HTTP 401 在 adapter 解析前由 `rejectUnauthorizedResponse` 标准化；Account Runtime 只接受当前 confirmed epoch 的第一次失效通知，迟到或并发重复 401 为 no-op，不补 Account probe、不重试原请求、不清 WebView Cookie。Account snapshot 天然不受 `forum` reset 影响，不迁移、不 preserve、不因自身结果换 key。`hosts` 只向 App 暴露 Account 自己生成的 host 节点、surface 状态和打开/关闭命令；公开 ReadPlan 不因核对 activity 暂停，登录 WebView barrier 打开时严格/private/write/notification fail-closed。
- 停用来源会关闭该站 auth surface、使 probe generation 失效并保留 Cookie、SecureStore 与最后可信身份；重新启用但没有持久化终态的来源进入 unknown/public lane，不自动核对，用户可在更多页显式刷新。
- NodeSeek、linux.do、妖火与 NodeImage 共用 `authSurfaceCoordinator`。打开页面只创建带来源、surface、generation、打开时 identity/epoch 的 ticket 并建立 barrier，不清 Cookie、不改身份、不删 Query；关闭按钮、系统返回、离开 More、切换 surface、NodeImage 成功或取消都先立即收起 UI，再异步对账对应站点。隐藏 surface 的重复关闭是 no-op；linux.do 因 App inactive 暂时卸载 WebView 不算逻辑关闭；已有权威检测结果的自动关闭复用该结果，不重复 probe。迟到 probe 只能提交给自己的 generation。
- 首页/读取触发的 linux.do Cloudflare 面板复用同一 WebView，但它是 read recovery，不进入 Account auth-surface barrier，也不修改账号 snapshot、session epoch、ReadPlan 或 query key。聚合 Feed 的其他来源先正常显示；用户每次显式“检测状态”只重试当前 exact Query 一次，成功后关闭，仍为 challenge 或普通失败则保持面板可重试，不递归拉起。
- 验证状态只能由协议或页面结构证据产生，不能由业务正文关键词产生。Cloudflare 的 `cf-mitigated: challenge` 是权威信号；缺少该 header 时只允许 HTML challenge 的 title、表单、Turnstile/Challenge DOM 或 script 作为 fallback。普通 `403`、`429` 或登录接口 `404` 本身不构成 challenge。明确非 HTML、JSON 形态正文、已识别的可读 NodeSeek 页面和妖火业务正文都先按业务数据处理；隐藏 WebView 同样先提交 JSON/可读页面，再判断 challenge。
- Feed、单站 Search、Topic 回复和 User 两个 lane 使用 Infinite Query；服务端 next page/cursor 与本次 `pageParam` 相同即停止，失败页不追加。LinuxDo Feed/Search 达到当前 `limit` 后直接使用服务器 cursor 决定 `hasMore`，不为探测第 `limit + 1` 条额外读取下一页；只有当前页过滤后不足且服务器仍声明下一页时才继续。LinuxDo `/site.json` 按 `public:omit` 或 `authenticated:<sessionEpoch>` 在 adapter 内保留一份进程 RAM 结果与 in-flight promise，Catalog、Feed、Search 同 scope 共享；scope 变化清除旧结果，不跨身份复用。每个 `UserRoute` 接收固定 `UserReference` 并实例化自己的 controller：已有 canonical id 才按当前 User Profile ReadPlan 启用 Profile；NodeSeek username-only 先启用严格 resolution Query，成功后才以 UID 启用 Profile 和两个 lane。分页复用同一 UID，不重复 resolve；route inactive、卸载、ReadPlan scope 和 epoch 变化取消旧 resolution/Profile，迟到结果只留在旧 key。刷新在未解析或错误时重试 resolver，已解析时只刷新 canonical Profile；解析成功前不显示关注。普通无匹配、非法响应、网络和 429 留在 App 且零自动重试/外开，只有用户显式“原站”才外开。User 的 Profile Query 刚显示 next cursor 时，分页命令先确保对应 lane 已用同一 profile seed，再从 Query cache 的最后 page/pageParam 发起准确下一页，不能因 observer 提交稍晚而静默早退。Topic 回复下一页的验证恢复继续调用 `fetchNextPage()` 重试原 page/offset，首屏恢复才使用 `refetch()`。聚合 Search 使用启用来源的独立 `useQueries` 渐进结算，单站失败或 strict blocked 不能阻断其他来源。
- `ReplyCompleteness = complete | partial` 只描述当前回复窗口是否完整，不否定来源 adapter 已放入 `items` 的行。共享层按 page 顺序连接 `items`，不重解释来源自己的容器成员和完整性规则。正文、作者或时间为空只做展示降级；`partial` 保留已有 `items`，后续读取只由明确 cursor 或用户命令决定。V2EX 明确引用另携带作者约束：该 target 在提交窗口和列表定位前必须命中唯一身份，失败不替换可信窗口；此约束不扩展成对其他 adapter 已确认 target window 的额外否决。缺少 completeness 的旧结果保守视为 partial，不能因旧回复数不匹配清空整窗；错主题、错页、重复 cursor、空窗口与显式 target 的来源协议保持。

- 正文 `ContentFrame` 从既有样式扣除实际 border/padding，列表另扣 marker 缩进，再通过 `ForumContentWidthBoundary` 传给 HTML、图片、code/table/math；没有第二份宽度缓存。Native selection 只报告活动与所属 revision，route-local 返回边界持有取消命令，预览/composer 优先；旧 revision 事件丢弃，活动变化不改正文 context 或 manifest。共享表情按钮只替换失败项的加载 attempt，重进可见分类只重试失败项，成功节点和滚动位置不变。
- `ReplyOrder = oldest | newest` 是回复流的服务端遍历方向，不属于 `ReplyFilter`。`ReadGateway.getReplies` 同时接收 `order` 与 `ReplyWindowPosition(start | cursor | target)`；来源 adapter 负责各自尾窗、页内方向和 cursor 转换。NodeSeek 继续按 `postPageCount`、严格 pager、响应 `postPage`、既有 comment collection 与 location 投影确认窗口；重复 comment ID 的普通展示副本按原规则折叠并降为 partial，不给 floor 增加跨站冲突语义。linux.do 按 `post_stream` 的 post ID 选窗并以 stream offset 决定 cursor；普通 hydration 的非空已请求 ID 子集按 stream 顺序展示并标 partial；重复/未请求 ID、整窗空缺和错误 cursor 仍失败；target 有 post ID 时按 ID 命中，否则保持 post number 路由。妖火把 `div.list-reply/div.line1/div.line2` 既有 selector 结果视为回复集合，以 floor 和确认页驱动导航；空展示字段保留，`reid` 只来自删除链接且不承担通用去重或定位语义，显式 target 不接受合成 floor。V2EX 把同主题显式 `p=N` 页面分别投影为回复窗口：第一页可在仍有下一页时标为 complete，并保留可信总数与 next page；正序触边只读取该 cursor 页，倒序 start 只定位显式末页窗口，target 只沿显式页链接寻找。所有站点都不因旧回复数或普通稀疏返回自动补抓、重试或轮询。
- TanStack Query 拥有回复 pages、cursor、取消和同一 Query 的分页单飞；Controller 只持有 route/order、纯失败描述和一个 `replyWindowGeneration`。普通 previous/next 在 Query 已有请求时不再发 transport；target、整帖刷新和写后刷新先取消当前 Reply Query，随后仅在 route、Query identity、order 与 generation 仍一致时原子替换窗口，后发命令直接使旧结果 stale，不排队。来源计数或窗口不一致只降低 completeness 或结算本次错误，不触发隐藏的 Topic 计数刷新、自动重试或轮询；用户显式重试只重读相同回复窗口，显式完整刷新才重取 Topic。UI 只投影筛选、排序菜单、Loading、错误与边界；最后一个 `next` 结算后立即显示边界。编辑/删除的内部 refresh target 只允许精确 `comment-id` 或完整 `delete-path`，action key、目标页查找、乐观删除与权威刷新使用同一目标，floor 只表示窗口位置。NodeSeek 新回复用当前详情计数与已加载最高楼层计算下一楼页，单次 `newest + cursor` 回读后再以真实实体定位；该 hint 不替代来源页确认，失效时不补读。其他来源保持既有写后窗口语义，不猜 Discourse post number。写成功后只以 `refetchType: none` 失效精确 Query，权威窗口刷新是唯一后续 transport。
- V2EX 服从同一窗口模型：Topic Query 只读取主题 API 与第一页 HTML；若第一页节点有效且原站给出同主题下一页链接，则立即显示该 complete 窗口、可信总数和“加载更多回复”，不在后台读取第二页。每次 cursor 读取只访问对应显式 `p=N` 页面；该页单条 malformed、缺楼、跨页重复或计数变化只把当前窗口标为 partial，并保留其余有效行。后续页整页失败时保留此前窗口和同一游标的评论级重试。倒序、楼层定位和两种刷新复用通用 Reply Query 命令；静置不产生 timer、轮询、自动补齐或自动重试。
- Query 的内部状态只有在对应业务请求已经启用后才可投影为页面 busy；未提交 Search 的 disabled Infinite Query 即使 `isPending` 也不能禁用首次提交入口。
- 动态读取 outcome 是 controller/query 状态的只读投影，不是第二套网络状态：Feed 由 `useFeedController` 按当前 items、来源错误和 fetch 状态给出 `data/empty/partial/error/auth`；Search 直接按每个 group 的 items/error/nextPage/loading 投影同一词汇。Screen 只暴露当前请求 marker，Loading、未提交和旧请求不暴露终态；该层不改变 timeout、去重或重试。
- linux.do/NodeSeek 的 Topic 回复、楼层回复、回复编辑和 Markdown 私信统一进入 `StructuredReplyComposer`；妖火继续由独立 UBB/纯文本 `YaohuoReplyComposer` 负责，V2EX 不挂写入口。`ComposerBottomSheet` 只拥有蒙层、75% Sheet、同实例全屏、键盘/Back 和安全区；APK 内离线 WebView runtime 拥有 Tiptap 文档、CodeMirror 源码、选区、撤销栈、Markdown codec 和唯一一套通用 Tiptap UI。标题/列表/链接/表格等 GFM 控件共用同一实现，可见能力按站点发布协议投影：NodeSeek 与 linux.do 均展示原站支持的删除线，NodeSeek 仅隐藏原站未提供的下划线，linux.do 保留两者；Emoji/贴纸、投票、Stardust、模板和私有语法仍按站点区分。表格上下文菜单直接由当前 table selection 决定可见性与命令能力，锚定整张 `<table>`，不写入共享 Builder 或保存第二份 selection。Markdown 与 NodeSeek pending-poll sidecar 是唯一草稿边界，Tiptap JSON/HTML 不持久化也不发送。RN→Editor 只发送初始化、命令、模式、主题和 snapshot 请求，Editor→RN 只发送 ready、revision state、snapshot、受限 host action 和 error；所有 payload 经 Zod 严格解析，Cookie、CSRF、签名、session ticket、上传凭据和正文 diagnostics 永不跨入 WebView。输入不逐键过桥，停止 600ms 自动 snapshot，关闭、路由离开、后台、模式切换和提交前强制结算；提交只接受不旧于当前 revision 的 snapshot，renderer gone 只以最后确认 Markdown/sidecar 重载，不回退旧 TextInput。
- `StructuredReplyComposer` 的 WebView origin、CSP、导航和文档存储配置只隔离编辑器文档；它不得创建、切换或清理 Android WebView profile。具体禁用项和 `global-webview-state-owner` 门禁由 `docs/code-standards.md` 唯一维护。
- Editor runtime 的通用 GFM 与每种站点私有语法分别由 Tiptap extension/Markdown codec 持有：严格表格不允许 merge/width/color；Emoji/贴纸 marker 由内联原子节点只保存原始源码，预览由 extension-local NodeView 从当前目录解析，目录晚到只刷新已挂载视图，不改写 ProseMirror 文档。所有 block 私有节点通过同一插入函数在其他 atom 后建立尾随段落与文本选区，同类型选中节点才原位更新；StarterKit 的官方 TrailingNode 保证 INIT、编辑预填和源码重解析后的任意终止 block 后仍有可输入段落，不能用 GapCursor CSS 或站点分支掩盖。CodeMirror 与 Tiptap 的程序同步均不进入用户 undo history；源码未变化时不重建富文本文档，直接保留原 selection 与 BubbleMenu。linux.do poll、details、spoiler、footnote、date/time、formula、ToC、scrolling、Mermaid、Build Chart、Graphviz 和未知 paired block 保持结构或原始源码；poll 用户组通过受限 host action 在同一 writable ticket 前后并行读取 `/site.json` 与 `/session/current.json`，WebView 只接收经校验的组目录和 Staff 能力。动态模板只经 host action 读取后插入当前选区。NodeSeek pending poll 在编辑期只使用受保护本地 token/sidecar；提交方取得同 revision snapshot 和 writable ticket 后才创建远端 poll，并在每次成功物化后立即保存 `localId + fingerprint + remoteId` journal，回复失败的手动重试复用同 fingerprint，明确 create 失败可重试，结果不明 fail closed。journal 仅存储 key 不存在时默认返回空，合法空数组仍有效；读取、JSON、结构、任一条目或重复 localId 校验失败均阻断物化，不清空、不覆盖、不自动重发。新主题容器、分类、标签和 rank 不属于该模块。
- Topic 写操作只通过 Topic `useMutation` 入口进入 MutationCache；`scope.id = forum:{source}:topic:{id}` 让同一 Topic 串行、不同 Topic 可并发。所有回复、编辑、删除、互动、投票、上传与 NodeSeek 签到先经 `ensureWritableSession(source)` 取得 `{ identityKey, sessionEpoch }` ticket；当前身份 unknown 时才在执行前定向核对，换号、退出或 barrier 打开均终止且不自动重放。编辑目标额外绑定 `topicId + reply + ticket`，Query key 只能在 ticket 返回后按其 epoch 生成；提交、上传和 Query cancel 后均从该 epoch cache 复核回复仍存在且 `canEdit === true`。身份、epoch、route active 状态或权限变化时关闭编辑并清除 target，但保留文本草稿，文件选择、NodeImage Key、上传、optimistic update 与 transport 均不得触发。门禁位于用户确认之后、Query snapshot/optimistic update/文件选择/transport 之前，等待取消 Query、文件选择或写后刷新后还要复核 ticket。乐观 apply、rollback 和成功结果只修改 ticket 所属的精确 Topic/Replies cache；服务器已确认后 ticket 失效只记录 `stale + serverConfirmed`，不弹成功提示、不应用迟到结果、不回滚或重发，也不写新 epoch。写 transport 同样在 adapter 前拦截原始 HTTP 401：当前 ticket 只失效一次；403、429、Cloudflare、typed `login-required/login-expired/verification-required` hint、ordinary 和 permission 均只结算本次 mutation，零 Account probe、零自动重放、零 Cookie 清理。非幂等请求发出后不自动重试。
- NodeSeek Stardust 收款 marker 是回复正文节点，不是钱包模块：编辑器只验证当前 member、合法 Ref 和纯文本备注并生成本地 marker；`stardustMarkup` 在详情 DOM 的原位置把合法 marker 替换为 typed element，代码块与非法 marker 保持文本。`NodeSeekStardustCard` 始终渲染静态收款信息，list/status 成功时才补充统计，失败由 controller 的 diagnostic trace 记录而不进入卡片 UI。付款 controller 先用当前 ticket prepare，再由用户确认不可退回，确认且 credential generation 未变时单次 send；取消零 send，只有一次性已关闭或结果不明禁用，send 不自动重发。收款人、金额、Ref ID、备注和 origin 都不信任正文输入，origin 固定 NodeSeek。
- Cloudflare/WebView 恢复和凭据存储 transaction 是多步 workflow，仍可使用受限 generation 防止过期恢复落地；不得用它们重新实现 Query 已有的 dedupe、cache 或取消所有权。

### Discourse 字段规则

- 跨站身份、正文、时间、计数、标准权限和标准 action 状态进入公共模型；Feed、详情、回复或用户数据缺少其必需身份/正文时 adapter 必须报告解析失败，不能伪造。搜索命中缺少可靠主题作者时仍保留结果并让 UI 显示未知作者，不能把命中回复者或最后回复者冒充楼主。
- 头像、标签、展示计数等可选公共字段允许缺失，UI 按缺失状态降级；写权限缺失必须 fail-closed，不得因为字段没返回就显示操作。
- 当前只有 linux.do 拥有业务需要的站点独有字段，`src/domain/forum/models.ts` 以直接 typed `siteExtension` 承载 `boostCount` 与 `needsApproval`，不维护单成员 map 或重复的 source 判别字段。它只能由 linux.do adapter 写入、对应 presenter/行为 adapter 消费，不能塞进公共顶层字段，也不能使用无类型 `Record<string, unknown>` 绕过边界；第二种真实 extension 出现时再提升为可穷尽判别联合。
- `reactions[]` 与 `/emojis.json` 是标准 Discourse 语义：`discourseReactions` 负责 id、计数、图片 URL 和未知 id 的文字回退；linux.do 目录请求经 `readGateway` 和 `discourseRead` port 进入 adapter，由 adapter 绝对化并缓存。Topic 切站或卸载会取消旧请求，迟到结果不得落到当前站点；linux.do boost 不进入公共 reaction 模型。
- 仅用于 transport 或一次请求解析、UI 与业务都不消费的原始字段不进入领域模型。

### 新 Discourse 站点接入

真实接入第二个标准 Discourse 站点时，先在 `sourceCatalog` 显式声明 `managedSession` 与其他 capability，再在 `src/sources/<provider>/` 新增独立 adapter、鉴权、transport 及匿名/登录 contract tests；只有两个实现都成立后，才把当前直接组合提升为 source registry 或共享 seam。`SessionSource`、Gateway epoch 与 strict operation 的身份门禁都从 `managedSession` 派生，不维护第二份登录站点数组；公开能力仍由 ReadPlan 的 operation matrix 决定。若站点只使用现有语义，不应修改 Feed、Search、Topic 页面或公共领域模型；只有出现新的业务语义时才扩展公共语义，出现第二种重要站点私有字段时才把直接 typed extension 提升为判别联合并增加对应 presenter。这里不提供 runtime plugin、hook bag、adapter 继承或版本矩阵。

## 导航与状态边界

- `src/app/AppNavigator.tsx` 是唯一的路由拓扑事实源且不依赖 feature；`AppRoutes` 把七个 route entry 注入其中。`useAppRuntime` 的当前 `screen` 只由 NavigationContainer 的 route change 回调更新，页面跳转只能调用 `appNavigation` 的导航命令。
- `src/features/topic/TopicRoute.tsx` 以完整、可序列化的 `Topic` 参数创建 route-local session、Query、rendering、preview、actions、FlashList ref、草稿、筛选和滚动状态；`useTopicSessionController` 是该 route 内唯一 session owner，互动 controller 只通过其命令收尾写入，不复制 state。
- Topic A → Topic B、Topic → User 和 Topic → ReadingSettings 都由 native stack 保留原 route 实例。inactive route 关闭 Query 与交互、取消自身请求并暂停原图升级；session epoch 进入 Query key，旧身份结果不能写入新 scope。返回优先级由 `useTopicRouteBeforeRemove` 固定为图片预览、回复 composer、native pop；不存在 presentation cache、route snapshot 或手工 Topic back stack。
- `src/features/user/UserRoute.tsx` 以完整、可序列化的 `UserReference` 参数创建 route-local resolution/Profile/两条分页 Query；`UserScreen` 在该 route 实例内持有主题/回复筛选、列表 ref 与滚动状态。User A → User B、User → Topic 返回时由 native stack 恢复原实例；inactive route 取消请求且拒绝刷新、分页和验证恢复。

## 首页筛选

- 首页聚合页只显示阅读筛选：`全部`、`未读`、`已读`、`收藏`。
- linux.do 单站分类行右侧显示排序菜单，支持 `最新`、`热门`、`新·所有`、`新·话题`、`新·回复`；分类和排序同时进入请求 key，避免列表缓存串用。
- NodeSeek 单站在未选分类时支持 `新帖子`、`新评论`；V2EX 单站在未选分类时支持 `全部`、`最新`、`最热`。
- 新增首页筛选状态应先放进 `src/domain/forum/feedOptions.ts`，再通过 `src/features/feed/useFeedController.ts` 进入 `getFeed`。

搜索筛选入口和 sheet visibility 由 `SearchFilterSheet` 自持，打开时开始 draft/apply/reset 事务，来源表单只消费 `value/onChange`；`DiscourseFilterPickers` 自持 picker 可见性、输入防抖、候选 Query、取消和 stale response 拒绝。Search 主 controller 只拥有已提交筛选与搜索 Query，不接收 sheet/picker raw setter；历史、AI merge/error 和结果 list model 分别归自己的模块。

## 账号中心

- `src/features/account/useNodeImageAuthController.ts` 统一拥有 NodeImage Key 与授权 panel 两组状态/动作；`useAccountRuntime` 统一提供 auth-surface 协调、canonical Account 对账和同步 session runtime，并由两个稳定 callback 在同一 tick 先提交 NodeSeek/linux.do User-Agent ref、再提交 React state，child controller 不持有成对 writer。`AccountHosts` 在 Account 内组合 `AccountHost`、`HiddenBrowserHost`、`NodeSeekLoginHost` 与 `YaohuoLoginHost`，App 只挂载生成节点；route 导航与 Topic 返回优先级分别归 `appNavigation` 和对应 route。

- 更新的服务器发现结果与本地下载目标分别属于 `useAppUpdateRuntime`；检查不会替换本地目标。`appUpdateDownload` 独占私有 document/wz-update 文件与 AsyncStorage `app-update-download`（format 1、可信更新元信息、可选总大小），该键不进入 ReaderData 或备份。启动先恢复本地任务，再进行网络检查；可信路径只由 versionCode + SHA 生成，瞬时 phase 不落盘。完整 `.apk` 每次安装前重新校验，安装取消、权限跳转或启动失败保留文件；只有损坏、用户显式替换目标或确认已安装才限定清理。旧 cache 的同身份完整包先校验再迁入。后台下载仅尽力继续，无下载中心或系统服务，进程结束后手动续传。

- `CredentialSite` 是 `SessionSource` 的类型别名；credential diagnostics、vault 输入校验与空摘要遍历都直接使用 catalog 派生的 `sessionSources`。`src/platform/storage/credentialVault.ts` 使用现有 SecureStore 按站点隔离 managed 来源的账号密码；`src/domain/session/loginFormAdapters.ts` 仍以完整 `Record<CredentialSite, Config>` 分别声明可信登录路径和字段，只主动填入并触发输入事件，不提交。
- 网站 Cookie 与保存的账号密码是两套独立数据：清除网站登录不删除凭据，删除凭据也不退出当前网站登录。
- More 页 `服务器代理` 由 `src/features/more/components/NetworkProxyModal.tsx` 承载，配置 HTTP / SOCKS5 代理并执行完整 TLS、HTTPS hostname 与固定 204 HTTP 响应的连通性测试；显示耗时是整段往返时间，不是 TCP Ping。
- `src/sources/accountRead.ts` 是账号状态读取的来源根，只分发三个 provider `accountStatus` adapter；adapter 各自处理精确 endpoint、Cookie/授权证据和 `AccountStatusObservation` 的 logged-in/logged-out/unknown/verification 分类。`src/features/account/useAccountStatusController.ts` 负责本机终态恢复、按来源 single-flight 核对、终态提交与 view model 投影；核对 activity、远端错误或 Loading 不覆盖旧可信身份。普通冷启动不调用 Account adapter；只有一次性候选迁移、更多页手动刷新或登录 surface 关闭才定向核对。`src/features/more/useBackupStatusController.ts` 只负责备份导入导出。
- `src/features/account/useAccountController.ts` 负责 NodeSeek、linux.do、妖火登录页内的显式检测、账号密码填入和用户明确触发的登录清理；linux.do 等级由独立 controller 持有，NodeSeek 签到归账号中心。`authSurfaceCoordinator` 统一页面打开/关闭与自动对账。NodeSeek 与 linux.do 每次手动 probe 只接受当前 WebView 文档的私有 nonce 与 documentKey 三态结果，任何新文档 `onLoadStart` 都先作废旧 probe。
- 登录 WebView 的组件身份只由 surface ticket 和显式 renderer 恢复 generation 决定；凭据填入 attempt 只用于关联 probe / fill 回执，必须通过已挂载 WebView 的 `injectJavaScript` 发送，不能进入 React key 销毁当前页面。登录 Cookie 的删除只暴露为原生 `clearManagedLoginCookies(source)`，仅由用户明确“清除登录”调用并回读确认；NodeSeek/linux.do 保留 Cloudflare Cookie，其他站不受影响。普通读取不调用 `flush()`。
- NodeSeek 登录 WebView 对每个当前 attempt 只暴露 App 自有 `nodeseek-login-webview-settled`：成功、明确错误或代理阻断均可结算，Loading 不结算，并始终保留“刷新页面”。NodeSeek、linux.do、妖火的 12 秒 watchdog 一旦结算 timeout，就卸载当前 WebView generation；只有用户显式刷新才 remount，避免失败页面继续占用 renderer 或阻断原生 accessibility。这个 surface 供 Replay 验证 App 流程，不把第三方 DOM 或数据可得性写进产品状态。
- `src/features/account/useSessionController.ts` 负责 workflow、本地凭据 generation、按站 epoch 与显式清除事务，不再保存或回灌可传输的 Cookie header。旧版 `nodeseek-access`、`linuxdo-clearance`、`yaohuo-cookie-header` 只在准确原生读取成功后删除一次；迁移不写 WebView Cookie。
- `SiteSessionState` 只作为登录弹层、凭据 transaction 和验证/授权 workflow 的本地生命周期输入；Account canonical snapshot 持有账号事实，二者只在 `SiteSessionViewModel` 组合。`identityTrust` 只有 `confirmed | unknown | none`；核对 activity 不改变 `canWrite`，真正 unknown 或登录 surface barrier 才阻止严格操作。WebView userId、Cookie 摘要和授权回调都不能独立覆盖 canonical identity。
- NodeSeek 当前账号只由当前会话页面证明：优先只读取服务端注入的 `__config__.user`，不递归接受同一配置内的 `profile/detail/member` 等公开或无关对象；再读取当前首页或设置页的专属 self-account 结构。不存在的 `/api/account/getInfo?readme=1` 不得被当作当前账号端点；保存的 userId 和 `/api/account/getInfo/{id}` 公开资料只用于用户页与显示，不能证明登录。渲染完成后，配置对象自有 `user` 字段且精确为 `null`，或当前页同时准确呈现登录、注册游客控件，才提交 `login-expired`；缺字段、`undefined`、`false`、空对象、HTML 404、普通网络、CF、超时或解析不确定都只能产生 `check-failed`，不得授权清除登录 Cookie。Account transport 先保留具有明确身份证据的直连快路径；直连 SSR 只有帖子列表而无身份结论时才进入共享 WebView，active request 只暴露非敏感 `owner`。只有 `account` probe 在 document 建立后提前启动身份证据轮询，并保留 `onLoadEnd` fallback；幂等 request guard 防止双注入重复回传，普通 Feed/Topic/Search 仍在加载结束后注入。脚本必须等待 current user、精确匿名 runtime 或完整游客控件，不能以“内容可读”提前结算；精确匿名 runtime 只桥接紧凑内部标记，不回传整页。
- 三站不共享验证器，但共享登录证据语义：`logged-in` 必须由当前凭据端点的 current user 或站点专属 self-account 结构证明，`logged-out` 必须由该站协议明确约定的匿名结果或原始 HTTP 401 证明，其余均为 `unknown`。Cookie、旧 userId、Topic 作者、公开资料和普通业务文案不能证明身份。NodeSeek 先检查首页并按需回退设置页，以 `__config__.user` 对象 / self-account 结构证明登录，以渲染后配置对象自有 `user === null` 或同页准确登录与注册游客控件证明退出；直连已有明确证据时不启用 WebView，普通 403/404、CF、登录 URL、网络及解析失败均 unknown。linux.do 只用 `/session/current.json`，合法 current user 为登录、匿名 404 或原始 401 为退出，403/challenge/网络失败均 unknown，且不以 `_t` 存在作为前置条件。妖火先检查 `wapindex.aspx?sid=-2`，以 `div.top2` 本人导航及 `touserid` 证明登录；公开页无法证明身份时再读取精确 `waplogin.aspx?siteid=1000`，只有 `form[name=login][method=post]` 同时包含准确账号与密码字段才证明退出。完整登录 form 的退出证据优先于该页自带的 Gocaptcha/ImageCaptcha 资源；只有缺少完整登录 form 的独立验证页才是 `verification`。缺字段、错 URL、403/429、普通 HTTP 错误与普通“我的/欢迎”文字均 unknown；写操作在准确 action URL 即时读取 SID。Cookie 名只形成非敏感摘要，传输由原生只读 CookieJar 按准确 URL 完成。`unknown` 不清凭据、不发布登录/退出，并保留 Account Query 的上次可信 data 只读。
- 妖火写请求只接受 Cookie header 中唯一的有效 `sidyaohuo`：空值和 `-2` 忽略，重复的同值 scope 可合并，出现两个不同有效值则在本地失败且保持零 transport；回复 body 与删除 URL 必须使用同一个已确认 SID。
- 原站 WebView 的 Cookie jar 由网站与 Android `CookieManager` 持有，是 NodeSeek、linux.do、妖火受管请求 Cookie 的唯一事实来源。managed/authenticated React Native API 请求由 `ReadOnlyWebViewCookieHandler` 按准确 URL 读取，响应 `Set-Cookie` 的保存入口为 no-op；public ReadPlan 的 `native-no-cookie` lane 在最外层 transport 强制 `credentials: omit`，不得加载 credential、Cookie 或 managed WebView fallback。调用方不得维护 Cookie 名白名单、拼接 header、缓存传输值或在实时读取为空时回退旧快照。媒体请求必须携带由正文/用户模型给出的 `ForumMediaRequestContext`；每个合法 HTTP(S) 媒体请求统一获得对应媒体 `Accept`、Android WebView `User-Agent`、系统语言 `Accept-Language` 及内部 `X-WZ-Forum-Media-Source`/`X-WZ-Forum-Media-Identity`。Topic 媒体首跳请求的 `Referer` 只由最终文档 URL、元素/文档策略和媒体 URL 关系解析，`contentSource` 不参与，最终 `Referer` 或 `none` 纳入请求与缓存/协调身份；不再根据目标图床 Host 分支，不伪造 `Origin`/`Sec-Fetch-*`，也绝不在 JS 读取 Cookie。私有 identity 由进程 nonce 与 session epoch 组成，留在 Expo/Glide request model 和 cache key 中，使同进程同 epoch 可复用、换 epoch 不合并、重启不复用旧私有磁盘条目。原生 application interceptor 在发网前同时移除两个内部头，并给有合法来源标记的请求设置 request `Cache-Control: no-store`，使其既不读取已有的未分区 OkHttp cache，也不写入新条目。孤立 identity 头同样必须移除但不得把普通请求升级为媒体 Cookie/no-store 策略。普通无标记 API 的 HTTP cache 与 public 媒体的稳定磁盘 namespace 不变。只有首跳目标与内容来源匹配时才允许 Cookie，任一重定向离开来源后 policy 永久降级匿名，跳回也不恢复；跨论坛、未知 CDN、无效/anonymous 标记继续请求但不读 Cookie，读取异常同样 fail-closed。头像、正文、贴纸、link card、音频、视频、预览和保存共用这条边界；来源 epoch 只用于 request/cache identity，不从目标 URL 反推。账号检测、刷新、过期判定、fallback 和普通失败不得写入或删除原站 Cookie；只有用户明确点击该站“清除登录”时才允许定向过期并回读确认。Android 同进程的可见与隐藏 WebView 共用 `CookieManager`，原生桥只调用公开 API，不读取 WebView 私有数据库。
- Android WebView 共享认证资产的写权限只属于 Account 的显式按站清除事务；编辑器、预览器、read recovery 与普通站点页面即使不可见也只有页面状态权限。等价的进程级清理由 `docs/code-standards.md` 与架构门禁统一阻断。
- 当前身份 endpoint 与失效语义必须有可追溯来源：优先官方源码/文档，其次当前站点实际调用，再次成熟客户端；测试 fixture 或 mock 不能自行创造生产接口及其状态码契约。任何原站登录清理都是破坏性权限，只有明确用户操作可以授予；当前行为归产品地图，历史事故归回归语料库。
- 对账确认 A→B、A→anonymous 或 anonymous→B 时，先提交 probe 结果到稳定的 canonical Account snapshot key，再取消旧内容请求并递增目标站 session epoch；目标站及 `all` 私有 Query、Level/AI、Topic 服务端数据与 managed media 身份缓存一起失效，其他站不变。A→A 只更新确认时间并解除 barrier；unknown 保留旧 epoch、可信身份和已加载内容只读。Feed `all` 的 barrier key 可以刷新其他来源，但展示层仍合并同 epoch 旧聚合中 dirty 来源的可信条目；换 epoch 后不得再合并。Topic 的主题选择、滚动、筛选和草稿属于 mounted route 的本地 React state；User route 只保存 `UserReference` 定位字段，旧 resolution、Profile、正文、回复、头像、简介、等级与活动列表不得跨 epoch 复用。
- 未登录验收不在 App 内模拟身份或过滤 Cookie，而是在独立 AVD 上安装同一待测 APK，让 Account Query、CookieManager 和来源 adapter 走生产路径。该 AVD 不复制主设备数据、不登录论坛；Cloudflare 要求验证时可在 App 内原站 WebView 完成访客验证并保留 clearance。`verified` 只表示访客验证已通过，仍保持 `isLoggedIn=false` 并使用匿名来源协议，不能被 Replay 当作已登录或失败。默认/Release Replay 与未登录 Replay 分目录、分设备执行。
- 搜索协议由 operation-level ReadPlan 决定：V2EX 使用 SoV2EX，妖火远程搜索严格依赖已确认会话；linux.do 与 NodeSeek 只有 authenticated lane 调用原站搜索。两站 public lane 保持 `public:omit` cache scope，但 transport 固定为 `none`，Search Controller 只用 `URLSearchParams` 构造 exact `https://www.google.com/search?q=site:<forum> <keyword>` 并交给受控 Android Custom Tab，绝不调用 ReadGateway、解析 Google HTML 或进入 HiddenBrowserHost。单站提交立即打开，聚合搜索只按来源顺序展示两个已结算的外部入口而不自动弹窗；匿名态隐藏站内筛选。Custom Tab 的固定菜单“在阅坛中打开当前主题”通过 explicit mutable `PendingIntent` 把当前 URL 交给 `MainActivity`；拥有该原生模块的 config plugin 同时直接声明 `androidx.browser:browser:1.10.0`，不依赖 Expo 的传递依赖。App 仍用 `parseForumTopicDestination` 只接受既有 linux.do/NodeSeek 主题或楼层 URL，Google 页、首页、用户页、其他域名全部拒绝。没有第三方 HTTP(S) intent filter 或 App Links 声明，普通网页点击不会被 App 劫持；native provider 不可用时退回普通浏览器并明确只能浏览。会话切换只改变该来源 scope：旧结果不得泄漏，也不得异步打开浏览器。
- NodeImage 显式授权先对 NodeSeek 做 canonical Account preflight 并捕获 `{identityKey, sessionEpoch}`，随后以三个独立 WebView mount 执行 `nodeimage-session → nodeseek-cauth → nodeimage-verify`。每个 mount 只在精确顶层 URL 使用声明式 `injectedJavaScript + onMessage`：session 页已经渲染 `#apiKeyInput` 时直接读取这个 DOM 兜底，否则由现有 NodeImage Cookie 请求 `/api/user/api-key`；取得 Key 即保存并关闭，只有精确 `401 + application/json + 非空 error` 才进入 Connect。bridge 将 Native `onMessage.url` 只作为当前 phase 的 HTTPS source-origin 证据，兼容现代 origin-only 与旧 bridge 完整 URL；脚本每次发消息及接受 start 前都重读 `location.href`，并另报精确 `documentUrl`，并同时通过顶层窗口、固定页面、nonce、owner、epoch 与 credential generation 门禁。Connect 页每 500ms 重报 ready，合法 start 后立即停止；Native flow 只领取一次执行权，页面 lexical guard 继续保证 `/api/cAuth` 最多一次，ready 重试绝不等于网络重试。成功后自动切回 NodeImage 调用 `/api/auth/verify` 并取 Key。三个 phase 从各自文档挂载起分别有 30/60/30 秒 watchdog；超时立即终止并卸载 WebView，Connect 未开始时只明确本 flow 未发起连接，已开始时明确结果未知且可能占用一次，不自动重试。API 请求一旦得到 HTML 403、网络、5xx、解析失败或 200 缺 Key 就停止，不再读取 DOM 掩盖错误，也不推断 session 失效；页面以透明触摸层阻止按钮和刷新，不依赖 popup 或 `window.opener`。NodeSeek Cookie、NodeImage `session_id` 与 SecureStore Key 是三份独立状态，App 不复制或手写 Cookie。每次 flow 使用 128-bit 安全 nonce，异步初始化 single-flight；切换 surface 或关闭取消 pending opening。失败立即终止 flow，迟到消息不能继续推进；最终 reconcile 与 SecureStore 写入前后门禁仍全部生效，脱敏诊断只记录阶段名及 `state/reason=timeout`。
- linux.do 验证弹层由 `src/features/account/components/LinuxDoVerifyModal.tsx` 与 Account-owned `AccountHost` 承载。

## 消息与后台通知

- `src/domain/forum/sourceCatalog.ts` 的 `notifications` capability 派生 `NotificationSource`；三站 adapter 表必须满足完整的 `Record<NotificationSource, NotificationAdapter>`。V2EX 当前 capability 为 false，不创建占位 adapter；未来开启时由 TypeScript 强制补齐协议实现。
- `src/domain/notifications/models.ts` 只定义消息真实共性：跨站展示类型、来源稳定 ID、参与者、可选时间、远端已读、目标、opaque 来源分组/cursor、会话消息和可选回复能力；带 fetch、signal、timeout 与来源 credential 的 adapter I/O 契约归 `src/sources/notificationAdapter.ts`。目标语义分为 `topic` 与 `topic-post`：前者只有主题身份，后者必须至少有原站明确的 `postId` 或 `postNumber`；adapter 不得从通知类型、标题或主题 URL 猜具体帖子，route 也不得为 `topic` 制造 `ReplyLocationTarget`。`NotificationKind` 只负责跨站展示，不承担站点筛选；`NotificationCategory` 由每个 adapter 返回并解释，聚合页不传 category。`src/sources/notificationGateway.ts` 统一处理 canonical identity、取消、错误归一化及 `Promise.allSettled` 来源隔离；NodeSeek、Discourse 与妖火 adapter 只处理各自分类、传输、解析和明确成功 oracle。通知 gateway 复用既有底层 fetch、账号和错误能力，但不扩展前台 `ReadGateway` 生命周期，也不依赖 React 或 WebView fallback；同一 adapter 可由前台和 headless task 组合使用。来源解析必须固定真实协议边界：NodeSeek 详情以 `commentId` 为主身份，floor 只作首个页提示或缺 ID 时的降级；提示错误时按响应 `postPageCount` / pager 的有界页拓扑继续匹配 commentId，不依赖 `replyCount`；NodeSeek 列表只有明确 `viewed/is_read/read=true` 才表示已读，省略标记仍是未读；Discourse 同时读取顶层通知字段；妖火把时间与删除动作分开，并按 exact detail URL 解析官方 `.content` 的“内容”字段，写操作不得作为正文，聊天气泡保持独立，逐条已读复核保留原分类与原页。
- NodeSeek @我/回复列表以 `comment_id`（兼容 `message_id`）生成统一消息、详情、投递和 Topic target 身份；完整 `ReplyLocationTarget` 从 route 经 Controller/Gateway 原样进入来源 adapter，`commentId` 为强身份，floor/pageHint 仅为查找提示。原始列表行 `id` 只作为 `remoteReadId` 供 `markViewed` 使用，不能参与 Android 摘要去重。私信会话只有发送者明确为对方且原站未读时才进入系统投递；自己发送但对方未查看的行按已读展示。
- 聚合消息 Query 保留每页、每来源的结果与错误边界且不带子分类。单站分类 ID 进入 list Query key；切站先恢复 adapter 的默认分类，分类栏只展示 adapter 当次声明的项。UI 为每个聚合失败来源投影独立重试；`NotificationRoute` 只以失败页保存的该来源 cursor 调用 `listPage`，并只替换该页中同来源条目、cursor 和错误。重试绑定发起时 exact identity 与 route-owned cancel signal；失败页不是末页时，把恢复来源 cursor 传播到末页并重算 `hasMore`，否则该来源后续页不可达。不得为局部恢复调用 `listAllPage/refetch` 或重建整个 infinite query。
- 列表、分类与详情 Query key 均绑定 `source:userId`，单站列表额外绑定 category。正文、预览、会话和回复草稿只存在 TanStack Query 与 route/component state；草稿、待上传文件名和凭据不持久化、不写 diagnostics。身份 A→B 或明确退出时，清目标站单站消息 Query、可能含旧身份的聚合消息 Query、水位、草稿和 Android 摘要，其他来源单站状态保持不变；pending、unknown 或 challenge 只暂停来源访问并保留上一份可信身份/cache 与 route 内存草稿，但展示层只允许 active 来源条目，不能把 retained 私有 row 继续画出来或伪装成退出。身份 reconciliation 在每个可等待副作用返回后都必须复核当前 effect，失效 generation 不得继续 reset 水位或清 Query。详情 route 捕获条目所属 `identityKey`，并用 route-owned `AbortController` 把 expected identity 与 signal 传给 `loadDetail/markRead/markAllRead/replyToConversation/uploadReplyImage`；identity signature 变化或 unmount 时取消。私信图片先通过账号 runtime 取得 writable ticket，NodeSeek 再确认 NodeImage API Key，随后才打开 picker；每个 await 后复核 ticket/identity/abort。gateway 完成 access 读取后、I/O 前再次核对 signal、exact identity 和适用 scope；NodeSeek 复用 NodeImage client，linux.do 复用 Discourse `/uploads.json` action client，妖火私信不暴露未核实的附件入口。上传成功只插入草稿、不自动发送；回复不乐观插入，失败/未确认保留草稿，明确确认后才清空并失效详情、当前来源、聚合与未读快照。
- `src/platform/notifications/notificationStore.ts` 的 AsyncStorage 只保存全局/来源意图、公开身份键、每站最多 200 个投递 ID、baseline、最后成功/未读状态和 Android notification identifier，不进入 ReaderData 或备份。前台当前未读由每个 `source + identityKey` 独立 snapshot Query 直接拥有；新增来源或换号只启动目标 Query，不重读稳定 sibling。每个 `dataUpdatedAt` 只持久化一次并触发一次对应 foreground delivery；持久化 `unreadCount` 只在 Query 尚未结算或单来源失败时作为 identity 精确匹配的启动/失败 fallback。首次 opt-in 的来源集合显式锁定首发三站，未来 capability 新增来源默认关闭。NodeSeek 缺少远端 ID 时，只能从不含参与者/对端、标题、预览和列表顺序的稳定定位字段派生 opaque ID；同 timestamp 的多会话产生歧义时整组保守丢弃，不能改用 participant-derived hash。首次启用、重新启用和换号把 baseline 置为未建立，第一次扫描只记录不投递。
- `src/platform/notifications/notificationWorker.ts` 是前后台共用的投递 owner。前台在启动/恢复、普通页面约 5 分钟、消息中心约 60 秒先读取 snapshot，再只对成功来源执行同一身份门禁、cursor 扫描、baseline 和去重；snapshot 持久化按来源 all-settled，单次失败不能阻断其他成功来源。消息列表 Query 只在 route focused 时启用；隐藏 route 不继续一分钟轮询。前台所有页面的新 `mention/reply/private-message` 都生成 Android 每站摘要，消息中心可见性只改变刷新频率，不得跳过 system sink 后仍提交水位；不用 Toast。headless `src/app/notificationBackgroundTask.ts` 在模块顶层定义唯一 TaskManager task，每轮先恢复安全存储中的代理并应用到 native CookieJar；读取或应用失败整轮 fail-closed。权限撤销在账号 probe 前停止读取；随后每站 direct probe 当前身份，unknown、challenge、匿名或身份不一致均跳过。单站累计最多扫描 60 条，并在无下一页、cursor 重复或 deadline 时停止。摘要不含标题、正文或私信内容；native 摘要创建、compound Store commit 或旧槽 exact dismiss 失败都不能永久消耗本轮投递 ID。发送前及 native `NotificationManagerCompat.notify(tag, 0, notification)` 返回后再次确认开关和身份；JS 不再把 Expo schedule Promise 当作展示完成，ack 后只用一次 Store update 原子提交 delivered IDs 与 identifier，状态已变则撤销本次 exact identifier。
- Android 摘要提交使用 `source + identity` 派生的确定性 A/B 两槽，不增加新的持久状态。worker 只预览非当前 staged identifier 和本轮新 ID，不在 native ack 前写 Store；native present 与 transactional exact dismiss 共用一个单线程 Executor，`invalidate()` 只 graceful shutdown，已接受的 cleanup 会在可能迟到的 notify 后按 FIFO drain，提交失败则 Promise reject。每个 `source + identity` 的 worker 投递另有进程内 Promise single-flight；worker 在 probe 前以 Store current identifier 为唯一真值清理该身份的 base/A/B/source-only 其他槽，native ack 后再复核 canonical private access，并以 expected new IDs、previous identifier、identity 和 intent 做一次 compound commit，成功后才 exact-dismiss 旧槽。明确 stale/撤销失败时 compound rollback 精确恢复提交前的 baseline、完整 200-ID 水位和 previous identifier，rollback 成功后才撤 staged 槽；deadline 不能把 Store rollback 与 OS dismiss 拆成两个失序补偿：ack 后 commit pending 或已成功时都保留 staged，late outcome 只有明确 `committed=false`/reject 才 exact-dismiss，由下轮 Store-current reconcile 清旧槽或 orphan。顶层 worker 对 source settlements 做 deadline race 后准时返回，但同身份 single-flight lane 继续持有到已开始的槽位对账、channel 初始化、native present、Store 写入和必要 exact dismiss 全部结算；对账中部分撤销失败仍须等待其余撤销，未开始 commit 的迟到 present 在 ack 后才撤 staged 槽，下一轮 foreground/headless worker 不能趁 Store 仍为 old 时进入 reconcile。broad best-effort cleanup 仅用于关闭意图、换号或停用来源。强杀发生在 native ack 与 compound commit 之间时，Store 仍指向旧槽，下一次 eligible worker 会清 orphan 并重投同一远端 ID，最多重复覆盖而不会永久漏报；commit 后、旧槽撤销前强杀则由 Store current 保留新槽并清旧槽。不另建 startup cleanup owner、transaction log 或 pending 状态。
- 内容源 enabled set 是通知意图之外的上层 allowlist。停用来源时前台立即从列表、未读与投递集合移除，取消该站 Query，撤销 Android 摘要并清 baseline/delivered/unread/identifier，但保留全局/来源通知意图和账号身份；重新启用时恢复已有终态，没有终态则保持 unknown，用户手动核对确认后第一次扫描只建立当前 baseline，不补发停用期间消息。headless task 每轮从 `reader-settings` 读取 allowlist，并在读取、分页、记录、展示及 identifier 落库前后复核；最后一个 eligible 来源停用时注销后台任务。
- 三个消息 native route 由 native stack 持有返回；App 根硬件返回处理器不得把它们误送到 Feed。列表读屏文案包含来源、已读状态和动作，`PillRail variant="tabs"` 的视觉与触控布局至少 48dp×48dp；共享 Tab 与按钮文字同样消费 Reader fontScale。
- Android 通知由 `expo-notifications` 提供单一 `message-notifications` channel，锁屏可见性为 `PRIVATE`，small icon 为 `assets/notification-icon.png`，颜色为 `#1677FF`；App 入口安装 foreground handler，让本地摘要在前台任何页面进入系统 banner/list。图形来自 Lucide 官方 `bell.svg`，以 ISC 许可保留在 `assets/notification-icon.svg`，PNG 只含白色与透明像素。全局和三站开关默认关闭；OS 权限拒绝/撤销保留用户意图并注销后台任务。registration 额外接收 runtime 的 active 来源集合，不可读来源不能单独维持空任务；register/unregister 作为单一串行生命周期，以最后一次调用意图为最终状态。Android 配置只通过 `app.json` 的 config plugin 持久化，不手改 `android/`。

## 服务器代理

- 代理配置保存在 Android 安全存储，不进入备份 JSON。持久化加载先校验顶层结构、profile 字段与唯一 ID；enabled 必须对应有效 active profile。只有 key 不存在才使用首次默认值，读取、JSON 或结构损坏均阻断联网，不能归一为关闭后直连；用户明确关闭或删除配置的正常事务保持不变。
- 原生 runtime 安装后立即 fail-closed；代理 SecureStore 读取最多等待 3 秒，超时或失败进入明确 failed 状态并释放等待者，但本地 routes 已可使用。只有安全存储读取成功并完成一次完整 native apply，managed App 请求与 WebView 才允许发布代理或直连；native apply 自身保持权威，不用额外 JS deadline 把仍在执行的 apply 误判为可直连。启用、切换和关闭期间，App 请求与 WebView 都保持阻止状态；即使 JS 已先把 `enabled` 更新为 false，WebView 也必须等原生 clear callback 成功后才能加载。runtime unmount 会让自己的等待者 fail-closed，代理应用失败时不能静默回退直连。
- 原生 server 拥有全部 client/upstream socket，连接与 copy executor 均有固定上限；停止或 bridge 销毁时先拒绝新的 probe、取消受管 OkHttp、关闭旧 server/tunnel，再释放 worker。旧 bridge 不能停止或覆盖新 bridge 的 server/WebView 状态。
- WebView localhost relay 只监听 `127.0.0.1`，backlog 与并发上限均为 16，header 上限为 64 KiB，共享双向 idle deadline 为 120 秒：任一方向读到字节都会续期，只有整个 tunnel 双向静默才超时。connection worker 用该 deadline 的剩余时间等待双向 copy 结算；真正过期时关闭双方 socket，因此阻塞写不能永久占用 worker。`Socket.soTimeout` 只负责唤醒读侧，不拥有 tunnel 生命周期。它只接受标准 HTTP 80 与 HTTPS CONNECT 443，拒绝 userinfo、控制字符、空 host、非标准 numeric IPv4、IPv4-compatible/mapped IPv6 及 loopback/private/link-local/multicast/unspecified IP literal；合法公网 IPv6 转发给 HTTP upstream 时使用带方括号的 authority-form。非 CONNECT HTTP 只按唯一合法 `Content-Length` 转发首个 request body，拒绝 `Transfer-Encoding`、重复或歧义 `Content-Length`，剥离 keep-alive 后关闭连接，不能把同一 client socket 的后续请求直接透传给 upstream；停止、切换和超时关闭 client/upstream socket 与 copy task。apply identity 只含协议、host、port、username、password，显示名称或配置 ID 变化不重启 relay。普通 `ServerSocket` 无法可靠取得 caller UID，因此这些限制只是 hardening，不构成“只有本 App 可用”的认证；hostname DNS rebinding 与同设备恶意 App 尝试连接仍是残余风险。若产品未来要求同-App认证，必须单独采用可做 UID 归因的 `VpnService` 架构。
- Android 原生代理模块由 `plugins/withNetworkProxyModule.js` 写入生成目录，并通过 `app.json` 的 plugin 列表持久化。它在 `OkHttpClientProvider` 的基础 client builder 上安装媒体来源 interceptor 与只读 WebView CookieJar；该 Jar 满足 RN `CookieJarContainer` 类型契约，但拒绝 Networking 生命周期把 delegate 换回可写 handler。跟踪的 `.env` 固定 `EXPO_PUBLIC_USE_RN_FETCH=1`，SDK 57 不以 Expo fetch 接管 `globalThis.fetch`，JS 请求继续进入 RN `NetworkingModule → OkHttpClientProvider`。RN 0.86.3 声明 OkHttp 4.9.2，Expo Video 57 的 Media3 1.9.0 声明 4.12.0；Gradle 冲突解析后的唯一有效 OkHttp 为 4.12.0，不强制覆盖到 5.x 或回退 4.9.2。Expo Image 使用专用 clone，设置 `connectTimeout=15 秒`、`readTimeout=30 秒`、`callTimeout=0` 并安装图片 challenge 恢复器；完整响应体没有逐图总时限，Topic 正文图片、贴纸、iframe、音频与视频的无进展终态都由 route-local `TopicBodyMediaCoordinator` 统一管理。RN 基础 client 保持零总时限且不安装该恢复器。Android autolinking 将锁定的 `expo-file-system@57.0.6`、`expo-video@57.0.3` 与 `expo-image@57.0.4` 从源码构建；官方 `expo-build-properties` 同时拥有 React Native source build、release minify 与 resource shrink 配置，保证 `react-native+0.86.3.patch` 的 Kotlin adapter 进入真实 APK，不再维护自制 settings/Gradle 注入。Hermes 使用 SDK 57 / RN 0.86.3 默认的 Hermes V1 配对，RN patch 不改 `ReactAndroid/build.gradle.kts` 或 `compileOnly` 边界。fresh prebuild 后 `dependencyInsight` 必须显示 `react-android` 来自 RN 0.86.3 source project、Hermes 与 RN 0.86.3 对齐且无重复。`patches/expo-video+57.0.3.patch` 是 DataSource 与 `ReadNetworkVideoClientRegistry` 源码改动的唯一 owner，`patch-package` postinstall 在依赖源码漂移时让 `npm ci` 立即失败，config plugin 不再读取或改写依赖源码。普通音视频取 current provider，已取得 Native lease 的健康播放器按内部 generation header 精确取回该代 client；内部 header 在 DataSource 与 interceptor 两层移除。正文音视频用 Expo Video 的 `timeUpdate.bufferedPosition` 严格增长续期同一无进展 deadline，音视频仍不进入 Cronet 图片恢复。安全 `<audio src>` 或嵌套 `<source src>` 在 sanitizer 归一为原子 `forum-audio`，空源只保留 fallback；Topic - `ReadNetworkRuntimeGeneration` 是整个 App 的单一读取网络生命周期，不是 NodeSeek/linux.do 专属恢复器。每代持有新的 `ReadNetworkGenerationProxySelector`、Dispatcher、forum/media `ConnectionPool`、Expo Image client 与按需 Cronet media transport，稳定复用 CookieJar、当前代理 delegate 及基础 TLS/RN cache 语义。RN `NetworkingModule` 的 custom builder 每次创建请求时抓取 current generation；`OkHttpClientProvider` 动态返回 current media client，供 Expo Video 和其他 provider 消费；Glide registry 在主线程完成 current image client publication。四站新建的 fetch、图片和音视频因此统一切代，新增来源不应复制 runtime。NodeSeek 的合格 WebView fallback 与 linux.do 经 WebView 成功证明的 8 秒 watchdog fallback，是目前两个证据充分的 trigger adapter；其他来源已经消费通用能力，但在没有可验证故障证据前不自动触发。
- 全 App Native fetch 边界把已有 `BrowserFetchIntent` 映射为内部 `source + cancelClass`：前台正文读取是 `content`，后台 Account probe 是 `health`，写入/需保留的读取是 `retained`；WebView 不经过该标记。Native interceptor 在出网前移除内部 header 并把归属固化到 request tag，媒体继续使用既有 source/kind tag，旧的无 tag 同源 `GET/HEAD` 只作为兼容性 content fallback。每条可恢复 transport 在 direct request 开始前捕获自己的 `expectedGeneration`；source parser 延后确认时仍提交该旧代，JS recovery interface 显式校验并交给 Native CAS。另一来源已经先轮换时只同步 current generation，不得在 commit 时重读 current 后再轮一代。轮换以 `expectedGeneration` 做跨来源 single-flight/CAS：先完整构建并原子发布新代，Glide publication 成功后只取消旧代 trigger 来源的 `content GET/HEAD` 与对应非视频媒体，Bridge 不等待旧 call release；同站 `health/retained`、带内部 video kind 的请求、无关来源和所有写请求继续在旧代自然结算。新 owner 只能原子 retain Native current，JS snapshot 落后时 Native 返回真实 current 供其重试，播放器拿到 lease 后才创建，并把该 generation 交给 DataSource 精确选择同代 client。Topic 正文的 generation 事件提交给 `TopicBodyMediaCoordinator`：它为当前 `running` 工作集换一个 attempt 并重置无进展 deadline，仍受 running `<=4` 约束；普通 `displayed`、尚未获许可的 `waiting` 与已经终结的 `failed` 媒体不重放。唯一例外是 Topic 当前音频 session：它保留位置、暂停播放并在新代 lease 到手后用同一 player 换源，不自动续播。非 Topic 的 unmanaged player 保留自己的不健康状态恢复，健康 player 则持有旧代 lease，直到其卸载或之后失败才释放；中间发生其他来源轮换也不能覆盖这次待切代事实。只有 queued/running call、player lease 与仍持有 response body 的 Cronet call 全部归零且 Dispatcher 连续空闲 250ms 后，才清两个 pool、封闭并退休 Cronet、关闭 executor，退休竞态不得取消已登记 Cronet call，迟到 release 不得回写 current。发布失败回滚且不取消写请求，未发布代只做无诊断的后台清理，下一次合格 trigger 仍可重试。JS trigger 建立的同一 `traceId` 贯穿 Native `intent/publish/cancel/drain/finish` 与 JS state apply；Native 在构建前记录 intent，正常轮换只有同时收到 JS apply ack 且旧代 drain 后才写唯一 finish，JS 发起的 CAS no-op 则由 JS 在 apply 后写 finish；失败与回滚各自只写一次终态。JS 只向同 trigger 来源发布 generation，不失效 Query；当前预览页按自己的三槽 owner 局部恢复，已显示正文图片和健康视频不动，保存、上传及 mutation 不重放。
- 图片先走上述 OkHttp/Glide 快路径；只有幂等 `GET/HEAD` 收到精确的 `Cf-Mitigated: challenge`，专用 network interceptor 才懒初始化进程内当前 generation 的 bundled Cronet，并通过官方 OkHttp transport 流式重试一次。Cronet 不启用 HTTP body cache、不自行跟随重定向；非 challenge 响应交回外层 OkHttp，重定向继续经过既有同来源 Cookie 与离源永久匿名策略。直连不设置 App proxy override；代理启用或切换阻塞态时只指向现有本地 HTTP relay，并以 `DISALLOW_DIRECT` fail-closed。代理 generation 变化会取消旧 Cronet 请求，待响应体释放后关闭旧 transport；普通图片、普通 `403/429`、超时、写请求、API 和视频都不会启动 Cronet。插件只为 Cronet 500 引用而 compileSdk 36 不提供的四个可选平台 API 注入精确 R8 `-dontwarn`，禁止使用全局 `-ignorewarnings` 或 `android.**`。诊断只记录来源、generation、challenge、结果状态和耗时，不记录 URL、Cookie 或正文。
- Glide 网络流的 `ResponseBody` 由生成的 `CloseSafeGlideStreamFetcher` 明确拥有，`GlideUrl` 与 Expo `GlideUrlWrapper` 两种 loader 都必须使用它。成功响应在 Glide `cleanup()` 前保持可读；`cancel()` 原子取消 call 并关闭已接收 body，取消后的迟到响应只关闭、不回调，`cleanup()` 与 `cancel()` 任意顺序均幂等，非 2xx 在回调失败前关闭，wrapper 的 progress listener 不得丢失。body transform、`byteStream()`、`contentLength()` 与 stream wrapper acquisition 也属于同一 ownership transaction：任一步抛错都必须关闭当前 owner，并且最多回调一次失败。该资源所有权修复不通过升级 Glide/Expo 代替。
- NodeSeek 的透明动态贴纸是正文媒体的受限例外：普通视频继续使用 Expo Video/Media3，只有经精确来源、路径和扩展名验证的 `/static/image/sticker/*.(webm|mp4|mov)` 使用透明、禁交互且禁止跨顶层导航的 Chromium media island，并在 ready 前保留同源 PNG fallback。document identity 只绑定媒体 URL，React 重渲染和 App 前后台切换不得重建；页面可见性只暂停/恢复当前动画。静态或 GIF 贴纸仍由 Expo Image 渲染；混合段落即使因后续大贴纸拆行，前面的图片贴纸也必须保留专用 `forum-sticker` 路径，且该元素使用 block content model，不能落入 Android TextView 行盒。无显式宽高时，最终布局以解码后的真实像素比例为准并限制在 100dp 内，目录级尺寸只可作为首帧占位，不能覆盖真实尺寸；同媒体 session 的有界尺寸缓存保证再次进入首帧稳定。
- 静态/GIF sticker 的 custom element model、Expo Image renderer 与 2,048 项自然尺寸缓存分别由 `src/ui/content/forumStickerElementModels.ts`、`src/ui/content/ForumStickerContent.tsx` 和 `src/platform/media/imageDisplayDimensions.ts` 共享；Topic 正文/评论与通知详情只组合这一个渲染 seam。NodeSeek Markdown adapter 仅将共享表情目录中的精确 shortcode 转成受 sanitizer 约束的 sticker HTML，代码字面量、未知 shortcode 和普通图片不进入该转换。
- 块图通过 FlashList 的 `useRecyclingState` 通知实际布局变化；`skipParentLayout` 只比较当前实例已使用的自然尺寸，不从共享缓存推断该实例已经完成布局。同 URL 并存实例分别通知，暖态尺寸不变时跳过通知，比较为 O(1)，不增加尺寸缓存或订阅。
- 复杂 SVG 保持 Expo Image/AndroidSVG 原生快路径；只有原生解码失败后，生成的 `SvgRendererModule` 才用与 Expo Image 相同的专用图片 client 复取，因此只继承明确 challenge 的 Cronet 恢复，并继续按响应流读取至 1 MiB + 1 byte 即中止；React Native 不先物化无界响应。`src/platform/media/compatibleImageSources.ts` 是进程级、有界、按完整 request identity single-flight 的 artifact service，并不归 Topic coordinator 所有；正文、预览等 consumer 分别持有自己的订阅。最后一个正文 consumer 因 permit attempt 被替换、row unmount 或 route inactive 释放后，未启动的 work 从队列移除，支持 `AbortSignal` 的进行中 fetch 被取消；Native bridge 已开始且不可取消时只允许当前有界读取结算，返回后不得再启动海报渲染或向失效 consumer 交付。仍有同 identity consumer 时共享工作继续。模块只为门禁内的明确 SVG 建立共享 document artifact，尺寸取自已验证 XML 的真实根元素。模块在同一排队批次内复用一个串行、禁网、禁脚本和禁文件访问的 Chromium WebView，把原始 SVG 数据 URI 栅格化为有界 PNG 海报；队列空闲后立即断开引用并销毁 WebView，不保留已 measure/layout 的空白 renderer。正文仍由 Expo Image 显示；全屏预览的每个 physical slot 由 ResumableZoom 只变换 raster 或 SVG 海报，`animated` artifact 的隔离 document view 是同一 slot 内、缩放树外的绝对定位 sibling，只在当前项挂载，并始终保留同尺寸海报作为底层连续帧。poster 已 `onDisplay` 后，双指或双击缩放只把固定 1 倍的 document view 透明隐藏；poster 尚未显示则继续保留固定 1 倍动画，不能为了降载制造空白。放大和平移只变换海报，回到 1 倍后直接显示同一个 document view，不销毁 Chromium 或重新发网。固定 nonce 的本地 bootstrap 只回报内层 `<img>` 就绪/失败，原始 SVG 仍以不可执行脚本、不可导航、不可访问网络/文件的 data image 载入。Android 动态复杂 SVG 使用平台默认合成层；普通图片、静态 artifact 和相邻页都不创建全屏 WebView，相邻页失败不得预启动复取、海报或 Chromium，保存仍重新读取原始 SVG。海报与 artifact 都按完整媒体 request identity 有界缓存，session epoch 变化不得复用旧结果；原生文件 LRU 淘汰海报后只用 artifact 内的原始字节重建一次，不重新发网。不得把 WebView 插入正文树或任何 scale transform 子树，也不得把 SVG 变形后再次交给 AndroidSVG。
- 全局 `dispatcher.cancelAll()` 与两个 pool 的成对 `evictAll()` 只属于代理配置 transition 的 fail-closed 清理。普通站点恢复只允许取消旧代 trigger 来源中标记为 `content` 的幂等 `GET/HEAD` 与对应非视频媒体；同源后台 Account health、retained 请求、健康视频、无关来源和写请求都不得误伤。两个旧 pool 只能在 OkHttp 请求、player lease 与 Cronet active body 都 drain 后一起清理；Cloudflare、解析、账号失败和写请求不得触发恢复。
- 本地开发地址 `localhost`、`127.*`、`10.0.2.2` 和 `::1` 不走代理。
- `SvgRendererModule` 的兼容复取每次开始时都抓取 App current generation 的 Expo Image 专用 client，不得 lazy 缓存启动时 client；这样 SVG fallback 与普通图片一起切代。

## 数据边界

- ReaderData 内存事务只规范化变化的分区，未变化的 favorites/history/followedUsers/settings/deletedRecords 保持引用；加载、外部替换与备份导入仍完整校验。批删在本次事务内各复制一次目标 records/tombstones，统一按预计算时间稳定排序并裁剪；不存在的删除和空清理返回原对象，不入持久化队列。串行保存、失败回滚和恢复模式不变。
- Topic 媒体逻辑 key 不等于注册实例：每次真实注册有独立代次，snapshot 绑定完整注册描述及仍存活的注册实例，progress/settle/retry 同时检查代次与 attempt；回收 A→B→A、禁用重启和策略变化不能复活旧准入。注册/注销同微任务合并 recompute，gate/settle/retry/runtime rotation 仍立即计算；相同 idle snapshot 和相同 viewport observation 不提交新 state。注册代次不参与磁盘缓存身份或 attachment key。调度先选最多四个合规的不同 request identity（original 最多一个），再确保这些运行实例全部进入最多八个 warm 实例；暂停只保留仍合规的运行实例，未准入实例不建立 deadline。
- Feed 来源轮询使用 Map 首次来源顺序与 bucket 索引，聚合缓冲只追加到本次创建的数组。Search 的 pages 合并独立于 loading/error 外壳；User 主题与回复分别派生；Notifications 的可见列表只依赖 items 与有效来源集合。新增数据仍允许一次 O(n) 不可变输出，不维护第二份分页缓存。本机库、主题与通知排序逐项预计算时间后稳定排序，保留各入口的并列及缺失时间语义；评论查找先做作者/图片筛选，再只转换候选正文，不创建一次性全回复文本索引。
- 前台通知 delivery 用按来源合并的待办 Map，最多为支持的通知来源数；只有一个 worker，运行中的重复触发至多保留一次补跑。worker 对外仍按时限返回，但前台运行占位等待真实 source settlements（包含 pending commit 与 native cleanup）释放，不能把重复待办转移到下游 identity 串行队列。待办捕获 identity、epoch、来源生命周期与挂载代次，开始前及 worker 私有访问边界重新检查权限和有效性；相同未读数仍可触发读取，既有消息事务、时限与 native acknowledgement 不变。

- NodeSeek、linux.do、妖火网站 Cookie 只存在 Android WebView `CookieManager`；App 不持久化可传输 header。自动填入账号密码与 NodeImage API Key 等 App 私有凭据使用各自 SecureStore key。
- 消息正文、预览、参与者、私信会话、Cookie 和 token 不写 ReaderData、备份、AsyncStorage 或诊断；通知存储只保留前述开关、公开身份键、有限 opaque 投递 ID、成功状态与系统 identifier，fallback ID 同样不得编码参与者、私信对端、标题或预览。
- 服务器代理地址、用户名和密码只保存在 Android 本机安全存储。
- 搜索历史保存在 `AsyncStorage`，最多 20 条，单条最多 120 字符。
- 本机资料只通过当前 version 2 JSON 备份 / 恢复迁移；导入会限制 JSON 大小和嵌套深度。敏感字段过滤区分 schema 字段与 favorites/history/followedUsers 及其 tombstone 的合法 source:id 业务键；用户名包含 sid/token/proxy 不得丢记录或删除保护，记录内部敏感字段仍过滤。Topic URL 只由 `source + id` 重建，用户主页由 `source + id/username` 重建；avatar/media URL 只保留合法 HTTP(S) 的 origin + pathname，清空 userinfo、全部 query 和 hash。保存、加载、导入和导出共用同一 sanitizer。
- 进程级图片尺寸 cache 使用现有 `Map` 的 2,048 项 LRU，覆盖千图帖反向滚动的布局事实；原图 display revision cache 仍使用 512 项 LRU；compatible SVG artifact 使用 32 项 LRU。React render 与 `useSyncExternalStore.getSnapshot` 只做无副作用 snapshot read；图片自然尺寸在有效 `onLoad` 回调内同步写入，已知尺寸的 mounted image 与未完成占位共用 `min(自然宽度, 正文宽度)` 等比几何。media lease 只拥有未完成加载工作，不拥有已显示像素或行高；其他热项只由已提交 effect/subscription、显示/recovery 与写入提升。带 active listener 的 revision 暂不淘汰，最后一个 listener 解除时再收敛，并且只通知同 identity。诊断 raw refs 每 kind 上限 4096、issued refs 上限 8192，使用单调 sequence 防止淘汰后 ID 重用，原始 topic/user/media 值仍不进日志。

- `ReaderStyleContextValue` 只携带 `theme/settings`；App、各 feature、Avatar、TopicCard、导航和 ImagePreview 分别用本 owner 的 style factory，跨旅程 primitive 自带样式，不存在全局 feature style registry。
- `android/`、`.expo/`、临时截图、日志和 Cookie 数据库都不进入仓库。
